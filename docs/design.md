# 設計仕様

## 1. 何を守る設計か

- **申請した時点でマスタを書かない。** 管理者が明細を「完了」にしたときだけ書く
- **編集はすべて画面内のコレクション。** 申請するまで SharePoint には出ない
- **トランザクションが無い前提。** 反映は明細ごとに独立して行い、途中で失敗しても
  そこまでは反映済みとして扱う（`ItemStatus` が明細ごとに残る）

## 2. データの持ち方

マスタ 5 本と申請 2 本、設定 1 本。詳細は [data-model.md](data-model.md)。

```
PRM_Org1        組織区分1
PRM_Org2        組織区分2（多段階承認の要否 3 種を持つ）
PRM_Users       利用者
PRM_UserOrg1    所属（利用者 × 組織区分1）
PRM_Grants      権限（利用者 × 組織区分1 × 権限種別）
PRM_Requests    申請ヘッダ（1 申請 = 1 行）
PRM_RequestItems 申請明細（対象 1 件 = 1 行）
PRM_Config      設定（管理者グループ ID など）
```

### 申請の粒度

**行と明細は 1:1 ではない。** `Seq` が同じ行がまとまって 1 明細として表示・操作される。

利用者を 1 人削除すると、利用者本体・所属・権限が別々の行になるが `Seq` は同じなので、
画面上は 1 明細。行を分けているのは反映処理を単純に保つため。

- `GroupKind` / `GroupKey` … 画面で束ねる単位（`ORG1` / `ORG2` / `USER`）
- `EntityKind` / `EntityKey` … 反映する対象そのもの（`ORG1` / `ORG2` / `USER` / `USERORG1` / `GRANT`）

### 変更前と変更後

明細は `BeforeJson` と `AfterJson` を持つ。反映は `AfterJson` を読んでマスタへ書く。
`BeforeJson` は**再申請のときのずれ検出**に使う。

`ChangeText` は人が読むための文で、判定には使わない。

## 3. 権限の考え方

### 範囲

| 値 | 意味 |
|---|---|
| `NONE` | 権限なし（行を作らない、または失効） |
| `ALL` | その組織区分1 の組織区分2 すべて |
| `PICK` | `Org2Codes` に `;A0101;A0103;` の形で列挙 |

### 対象かどうか

**多段階承認の要否は組織区分2 だけが持つ。** 組織区分1 側には無い。

```
外部接続の対象   = org2.ApExt
無線LANの対象    = org2.ApWlan
クラウドの対象   = org2.ApCloud
それ以外の種別   = 上の 3 つのいずれか
```

要否が「不要」の組織区分2 は、その権限種別の対象外（画面では `―`）。

### 無効になった権限

要否を「要」から「不要」に変えると、そこに付いていた権限が宙に浮く。
**申請の前に外させる。** 該当のチェックを薄いピンクの網かけにし、外すまで申請できない。

### 承認できる人がいない組み合わせ

要否が「要」なのに、その組織区分2 に誰も権限を持っていない状態。
組織名の部分を網かけにして知らせるが、**申請は止めない**（運用で埋める前提）。

## 4. 申請の流れ

```
編集（コレクション）
   ↓ 申請
PRM_Requests 1 行 + PRM_RequestItems n 行   状態 = SUBMITTED / PENDING
   ↓ 確認中にする
                                            状態 = INPROGRESS
   ↓ 完了にする（明細ごと）
AfterJson を読んでマスタへ書く              明細 = DONE
すべて DONE なら                            申請 = APPLIED
一部だけなら                                申請 = PARTIAL
```

差し戻し（`REJECTED`）と取り下げ（`CANCELED`）は**何も反映しない**。

### 申請種別

かごの中身から決める。

| かごの中身 | `ReqType` |
|---|---|
| 組織区分1 だけ | `ORG1` |
| 組織区分2 だけ | `ORG2` |
| 利用者だけ | `USER` |
| 混在 | `MIXED`（表示は「複数種別」） |

利用者の画面からの申請は `USER` / `GRANT` / `MIXED` を中身から決める。

## 5. 再申請とずれ検出

差し戻された自分の申請だけ、内容を読み戻して申請し直せる。元の申請はそのまま残り、
再申請すると新しい申請番号になる。

**読み戻すもの**

- 組織区分2（追加・変更・削除）
- 新規利用者
- 権限

**再申請させない条件**

| 判定 | 見るもの |
|---|---|
| ずれ | 明細の `BeforeJson` と現在のマスタを突き合わせる |
| 別の申請 | 同じ対象に `PENDING` / `READY` の明細が別の申請番号で出ていないか |

ずれの比較対象。

| 種別 | 比較する項目 |
|---|---|
| 組織区分2 | 日本語名称・英語名称・表示順・多段階承認の要否 3 種。追加なら「コードが既に使われている」 |
| 利用者 | 氏名・メールアドレス・部署名 |
| 権限 | 範囲と組織区分2 の並び |

## 6. 利用者の登録

**Entra ID から引き当てる。** 氏名かメールアドレスで `SearchUserV2` を呼び、
1 件なら即反映、複数なら候補から選ぶ。`UserProfileV2` で氏名・部署・オブジェクトIDを取る。

氏名・メールアドレス・部署名は**入力できない**。AD の値だけが入る。
グローバルID は Entra ID に無いので手入力。

取得した `AdObjectId` はマスタまで書く。**これが無いと、その人がログインしても
自分だと認識されない**（`PRM_Users.AdObjectId` と Entra ID のオブジェクトIDを突き合わせている）。

## 7. 利用者の削除

**削除もかごを通る。** 他の変更と同じく「申請」を押すまで確定しない。

- 「ユーザを削除」で `colDelU` に入り、かごに「利用者の削除」の行が出る
- 入れた時点でその利用者の権限は編集できない
- **他の変更が既にかごにある利用者は削除できない**（先に申請するか取り消す）
- 申請すると、利用者本体・所属・権限の失効を 1 明細（同じ `Seq`）として作る

### 削除申請中の扱い

削除を申請したあと、その利用者の詳細を開くと

- ボタンが「**削除を取り消す**」に変わる
- 権限の編集が塞がれる（覆いを掛ける）
- 取り消すと申請と明細が `CANCELED` になり、編集できるようになる

一覧では利用者名に取り消し線が付く。

## 8. 元に戻す / やり直す

**画面（タブ）ごとに独立した履歴**を持つ。表示中の画面の変更だけを戻し、
別画面のものには触らない。

| 範囲 | 対象のコレクション |
|---|---|
| 組織マスタ タブ | `colO1Edit`（今の組織区分1 の行）/ `colO2Edit`（今の組織区分1 の行） |
| ユーザマスタ タブ | `colGEdit`（今の組織区分1）/ `colNewU` / `colUEdit` |
| 利用者の画面 | `colGEdit` / `colNewU` / `colUEdit` / `colDelU`（その利用者の行だけ） |

1 手ごとに `{S:手数, R:行}` の形で丸ごと控える。列を並べ直すとコレクションの型が
変わってしまうので、行をそのまま持つ。

履歴を作り直すのは、画面に入ったとき・組織区分1 を切り替えたとき・読み直したとき・申請したとき。

## 9. 実装上の約束事

Power Fx とモダンコントロールで踏んだ制約。破ると**黙って動かなくなる**ので守る。

| 約束 | 理由 |
|---|---|
| **`If` の引数に `;` の連結を入れない** | 式がエラーになり、押しても何も起きなくなる。分岐は隠しボタンに分けて `Select()` で呼ぶ |
| **`ItemDisplayText` に式を置かない** | 列の参照しか受け付けない。表示用の文字は `Items` の側で作る |
| **選択肢列の絞り込みに `\|\|` を使わない** | 委任されず全件を引く。等値 1 本ずつに分ける |
| **無いプロパティを書かない** | 取り込みは通るのに Studio で `PA2108` になる。`check-yaml.py` が検査する |
| **式の一部を消したら括弧を数える** | 閉じ括弧だけ残ると `予期しない文字があります` になる。`check-yaml.py` が検査する |
| **モダンの文字は既定で上下に余白が入る** | 高さが足りないと内側にスクロールバーが出る。余白を 0 にして高さを確保する |
| **コネクタの列名は関数ごとに違う** | `UserProfileV2` は camelCase、`SearchUserV2().value` は PascalCase |

詳細と出典は [cli.md](cli.md) と [powerapps-controls.md](powerapps-controls.md)。

## 10. 反映と公開

`pac solution import` はアプリの**保存された版**を更新するだけで、
利用者に配られる**公開された版**は変わらない。`deploy.ps1` は取り込みのあと
`Publish-AdminPowerApp` で公開まで行う。

環境変数 3 つ（`PERMHUB_SP_TENANT` / `PERMHUB_SP_APPID` / `PERMHUB_SP_SECRET`）が
そろっていればサービスプリンシパルで無人サインイン、無ければ対話サインイン。
Windows PowerShell 5.1 が無い環境では公開を飛ばし、Studio で公開するよう促す。

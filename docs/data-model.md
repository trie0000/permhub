# リスト構造（SharePoint）

[spec-permission.md](spec-permission.md) の仕様を保存するためのリスト設計。

---

## 0. 設計方針

### 現行値と履歴を分ける

| | 役割 |
|---|---|
| **現行値テーブル**（マスタ・権限） | 「今どうなっているか」。画面はここだけ読む |
| **申請テーブル**（ヘッダ・明細） | 「いつ誰が何をどう変えたか」。追記のみ、更新しない |

履歴を毎回たどって現在値を組み立てる方式（イベントソーシング）は取らない。
SharePoint は結合ができず件数も伸びるので、一覧表示が実用的な速度にならない。

### 申請の確定 = 現行値の更新 + 明細の記録

**この 2 つは必ずセット。** 片方だけ成功すると履歴と実態がずれる。
SharePoint にトランザクションは無いので、§6 の手順で担保する。

### 内部名は英語

列の内部名は英語、表示名だけ日本語。
`CreateFieldAsXml` の `Options` に `AddFieldInternalNameHint`(8) を含めないと内部名が
日本語エンコード（`_x540d__x79f0_`）になり、数式から参照できなくなる。

## 2. マスタ

### `PRM_Org1` 組織区分1

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | 組織区分1コード | **一意 + 索引** |
| `NameJa` | Text | 日本語名称 | |
| `NameEn` | Text | 英語名称 | |
| `SortOrder` | Number | 表示順 | |
| `IsActive` | Boolean | 有効 | 既定 true |

### `PRM_Org2` 組織区分2

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | 組織区分2コード | **一意 + 索引** |
| `Org1Code` | Text | 親の組織区分1コード | **索引** |
| `NameJa` | Text | 日本語名称 | |
| `NameEn` | Text | 英語名称 | |
| `SortOrder` | Number | 表示順 | |
| `ApExt` | Boolean | 多段階承認要否（外部接続申請） | |
| `ApWlan` | Boolean | 多段階承認要否（無線LAN申請） | |
| `ApCloud` | Boolean | 多段階承認要否（クラウド申請） | |
| `IsActive` | Boolean | 有効 | 既定 true |

**「有効な多段階承認」はどこにも保存しない。** 組織区分1 と組織区分2 の AND なので、
保存すると組織区分1 を変えたときに全件更新が必要になり、必ず食い違う。**都度計算する。**

```
有効Ext(org2)   = org2.ApExt
有効Wlan(org2)  = org2.ApWlan
有効Cloud(org2) = org2.ApCloud
```

### `PRM_Users` 利用者

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | グローバルID | **一意 + 索引**。手入力（AD には無い） |
| `FullName` | Text | 氏名 | AD から取得して焼き込み |
| `Mail` | Text | メールアドレス | 索引（検索用）。AD から |
| `Department` | Text | 部署名 | AD から |
| `AdObjectId` | Text | AD オブジェクトID | **索引**。AD 突合用の副キー |
| `SyncedAt` | DateTime | AD 最終突合日時 | 棚卸し用 |
| `IsActive` | Boolean | 有効 | 既定 true |

メールアドレスはキーにしない。**変わりうるうえ、変わったときに権限側の参照が全部壊れる。**

### `AdObjectId` が要る理由

グローバルID は AD に無いので、**マスタと AD をつなぐものが何も無い状態**になる。
メールアドレスで突き合わせる手もあるが、**メールが変わった瞬間に同一人物と判定できなくなる**
（改姓・転籍でよく変わる）。そうなると棚卸しで「AD に居ない人」として誤検知する。

`Office365Users` が返す `id`（オブジェクトID の GUID）は**不変**なので、これを保存しておく。
利用者登録申請で AD から人を選んだ時点で一緒に焼き込む。

### `PRM_UserOrg1` 所属

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | `<グローバルID>#<組織区分1コード>` | **一意 + 索引** |
| `GlobalId` | Text | グローバルID | **索引** |
| `Org1Code` | Text | 組織区分1コード | **索引** |
| `IsActive` | Boolean | 有効 | 既定 true |

**`Title` に複合キーを入れて一意制約をかける。** SharePoint に複合一意キーは無いので、
文字列連結で代用する。これがないと同じ所属が二重登録される。

## 3. `PRM_Grants` 権限（現行値）

**1 行 = 利用者 × 組織区分1 × 権限の種類**

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | `<グローバルID>#<組織区分1コード>#<権限コード>` | **一意 + 索引** |
| `GlobalId` | Text | グローバルID | **索引** |
| `Org1Code` | Text | 組織区分1コード | **索引** |
| `RoleCode` | Choice | 権限 | `SECMGR` `CONFORM` `EXTCONN` `WLAN` `CLOUD` `INFOSEC` |
| `ScopeType` | Choice | 範囲 | `ALL` 全体 / `PICK` 個別 |
| `Org2Codes` | Note | 組織区分2コード（;区切り） | `PICK` のときのみ |
| `CompanyRole` | Choice | 権限種別 | `PRIMARY` 事業会社(正) / `DEPUTY` 事業会社(副) / 空 |
| `IsActive` | Boolean | 有効 | |
| `LastReqNo` | Text | 最終更新申請番号 | **索引** |

### Choice の値は英語コードにする

表示は日本語、保存は英語コード。**表示名を変えたくなったときにデータを触らずに済む。**
日本語を保存すると `ScopeType = "全体"` のような比較が数式に散らばり、
名称変更のたびに全部直すことになる。

### `Org2Codes` は Note（複数行テキスト）

`;A0101;A0103;` の形式。**前後を含めて区切り文字で挟む。**
`";" & コード & ";" in Org2Codes` で部分一致の誤判定を防げる
（`;A010;` が `;A0101;` にヒットするのを防ぐ）。

1 行テキスト（`FieldTypeKind 2`）は **255 文字で HTTP 500** になるので使わない。
組織区分2 が数十件になると簡単に超える。

### `ScopeType = ALL` のとき `Org2Codes` は空にする

配下の組織区分2 を展開して保存しない。**マスタが増えたときに追随できなくなる。**
「全体」は常に**参照時に展開**する。

## 4. 申請

### `PRM_Requests` 申請ヘッダ

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | 申請番号 | **一意 + 索引**。`REQ-20260720-0001` |
| `ReqType` | Choice | 申請種別 | `ORG1` `ORG2` `USER` `GRANT` `MIXED`（1 申請に複数種別が混ざるとき） |
| `TargetKey` | Text | 対象キー | **索引**。権限変更ならグローバルID、マスタならコード |
| `TargetName` | Text | 対象名称 | 一覧表示用のスナップショット |
| `Summary` | Note | 申請内容の要約 | 一覧に出す 1 行 |
| `ApplicantId` | Text | 申請者グローバルID | 索引 |
| `ApplicantName` | Text | 申請者氏名 | |
| `SubmittedAt` | DateTime | 申請日時 | **索引**（期間検索用） |
| `Status` | Choice | 状態 | **索引**。`SUBMITTED`(申請済み) `INPROGRESS`(確認中) `PARTIAL`(一部完了) `APPLIED`(完了) `REJECTED`(差し戻し) `CANCELED`(取り下げ) `ERROR` |
| `ItemCount` | Number | 明細件数 | 突合用 |

`TargetName` は**申請時点の名称を焼き込む**。マスタが後で改名されても、
当時の申請書を当時の名前で読める。参照にすると履歴が書き換わってしまう。

### `PRM_RequestItems` 申請明細

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | `<申請番号>-<連番3桁>` | **一意 + 索引** |
| `ReqNo` | Text | 申請番号 | **索引** |
| `Seq` | Number | 連番 | |
| `Operation` | Choice | 操作 | `ADD` `UPDATE` `DELETE` |
| `EntityKind` | Choice | 対象種別 | `ORG1` `ORG2` `USER` `USERORG1` `GRANT` |
| `EntityKey` | Text | 対象キー | **索引**。現行値テーブルの `Title` と同じ値 |
| `BeforeJson` | Note | 変更前 | `ADD` のときは空 |
| `AfterJson` | Note | 変更後 | `DELETE` のときは空 |
| `ChangeText` | Note | 変更内容（人が読む） | |
| `ItemStatus` | Choice | 明細の状態 | **索引**。`PENDING` `READY` `DONE` `REJECTED` `CANCELED`（既定 `PENDING`） |
| `ItemNote` | Note | （旧）差し戻し理由 | **使わない**。理由は `PRM_Requests.DecisionNote` に持つ |
| `GroupKind` | Text | 明細の種類 | `ORG1` / `ORG2` / `USER`。**表示と操作の単位** |
| `GroupKey` | Text | 明細の対象 | 組織区分1 コード／組織区分2 コードを `;` で並べたもの／グローバルID |
| `HandledAt` | DateTime | 状態変更日時 | |
| `HandledBy` | Text | 状態変更者 | グローバルID |

### なぜ JSON スナップショットか

項目ごとに 1 行にする案（`項目名 / 変更前 / 変更後`）と迷うところ。JSON を選んだ理由:

- 権限 1 件の変更で「範囲」「組織区分2」「正副」が同時に変わる。項目行に割ると **1 変更が複数行に散る**
- SharePoint は結合できないので、散った行を組み直すのが面倒
- **当時の状態を丸ごと復元できる**。項目行だと保存しなかった項目が消える

代わりに人間可読性が落ちるので、`ChangeText` を併記する。

```
BeforeJson: {"ScopeType":"ALL","Org2Codes":"","CompanyRole":"PRIMARY"}
AfterJson:  {"ScopeType":"PICK","Org2Codes":";A0101;A0103;","CompanyRole":"DEPUTY"}
ChangeText: 外部接続申請担当（東日本ブロック）
            範囲: 全体 → 個別（北海道支店, 関東支店）
            権限種別: 事業会社(正) → 事業会社(副)
```

`ChangeText` は**コードではなく申請時点の名称で書く**。あとで読む人はコードを知らない。

## 4.5 `PRM_Config` 設定

テナント固有の値をコードに書かないための逃がし先。1 行 1 キー。

| 内部名 | 型 | 表示名 | 制約 |
|---|---|---|---|
| `Title` | Text | 設定キー | **一意 + 索引** |
| `Value` | Text | 値 | |
| `Descr` | Text | 説明 | |

| キー | 用途 |
|---|---|
| `AdminGroupId` | 管理者にする Teams（Microsoft 365 グループ）の ID。空なら申請履歴に管理者向けの操作が出ない |

グループ ID は、そのチームの SharePoint サイトで `/_api/site?$select=GroupId` を開けば分かる。
**ID をアプリの数式に直書きしない**（テナントを移すたびに作り直しになる）。

## 5. 履歴の引き方

| 知りたいこと | 引き方 |
|---|---|
| この申請で何を変えたか | `PRM_RequestItems` を `ReqNo` で絞る |
| この権限はいつ誰が変えたか | `PRM_RequestItems` を `EntityKey` で絞り `Seq` 順 |
| この人の権限変更履歴 | `PRM_Requests` を `TargetKey = グローバルID` で絞る |
| この組織区分2 の変更履歴 | `PRM_RequestItems` を `EntityKey = 組織区分2コード` で絞る |
| 直近の変更理由 | `PRM_Grants.LastReqNo` → `PRM_Requests` |

**`EntityKey` に索引を張るのが要。** ここが無いと権限 1 件の履歴を出すのに全件走査になる。

## 6. 申請と反映（トランザクションが無い前提）

**申請はマスタに触らない。** 申請ボタンは記録だけ行い、マスタへの書き込みは
管理者が明細を「完了」にした時点で行う。

### 申請（申請者）

1. `PRM_Requests` に `Status = SUBMITTED` でヘッダを 1 本作る → 申請番号が確定
2. 変更 1 件 = 明細 1 行として `PRM_RequestItems` に投入（`ItemStatus = PENDING`）
3. **マスタは書かない**

1 回の申請で組織マスタと利用者マスタの変更が混ざってよい。混ざったヘッダは
`ReqType = MIXED` になる。

### 反映（管理者）

状態は**申請まるごと**で動かす（明細ごとの操作は UI から外した）。
マスタに書くのは `DONE` にした瞬間だけ。

| 明細の状態 | 意味 | マスタ |
|---|---|---|
| `PENDING` | 未対応 | 触らない |
| `READY` | 確認中（内容 OK、作業前） | 触らない |
| `DONE` | 完了 | **このとき `AfterJson` を当てる** |
| `REJECTED` | 差し戻し | 触らない（理由は `DecisionNote`） |
| `CANCELED` | 取り下げ（申請者が引っ込めた） | 触らない（理由は `DecisionNote`） |

`DONE` にする処理は「`AfterJson` を `ParseJSON` して対象マスタに `Patch`」。
明細が正・マスタが従なので、**同じ明細を当て直しても同じ結果**になる（べき等）。

### ヘッダ状態のロールアップ

明細をまとめて 1 つの申請者向け状態に畳む。

```
未決（PENDING/READY）が 0 件:
  すべて DONE      → APPLIED   （完了）
  すべて REJECTED  → REJECTED  （差し戻し）
  すべて CANCELED  → CANCELED  （取り下げ）
  混在             → PARTIAL   （一部完了）
未決あり:
  DONE/REJECTED/CANCELED/READY が 1 件以上 → INPROGRESS（確認中）
  それ以外                                 → SUBMITTED （申請済み）
```

取り下げは「申請者本人・全明細が `PENDING`」のときだけなので、実際に起きる
`CANCELED` は必ず全明細が揃った状態になる。

### `AfterJson` は反映の契約

`AfterJson` は表示用ではなく**反映処理の入力**になる。対象種別ごとに次の形で書く。
足りない項目があると反映時に blank で上書きされるので、増やすときは
書き込み側（申請）と読み込み側（反映）を同時に直す。

| 種別 / 操作 | `EntityKey` | `AfterJson` |
|---|---|---|
| ORG2 / ADD | 新コード | `{"Org1Code":"…","NameJa":"…","NameEn":"…","SortOrder":n,"ApExt":b,"ApWlan":b,"ApCloud":b}` |
| ORG2 / UPDATE | コード | 同上（`Org1Code` は無くてよい） |
| USER / ADD・UPDATE | グローバルID | `{"FullName":"…","Mail":"…","Department":"…"}` |
| USERORG1 / ADD | `<gid>#<org1>` | `{"GlobalId":"…","Org1Code":"…"}` |
| GRANT / ADD・UPDATE | `<gid>#<org1>#<role>` | `{"GlobalId":"…","Org1Code":"…","RoleCode":"…","ScopeType":"…","Org2Codes":";A0101;"}` |
| すべて / DELETE | 同上 | `{"IsActive":false}` |

名称のような自由入力は、JSON に埋める前に二重引用符をバックスラッシュ付きに置換する
（Power Fx なら `Substitute(<値>, 二重引用符, バックスラッシュ+二重引用符)`）。
壊れた JSON は表示崩れではなく**反映の失敗**になる。

### 組織区分2 を追加する申請のコード

コードは**申請時に採番して明細に載せる**（画面には「未割当」と出す）。
反映時に採番すると、同じ申請に含まれる権限明細が参照しているコードとずれる。

採番の元は「`PRM_Org2` の全件（無効も含む）＋ 画面の編集中 ＋ **未反映の申請明細**」の最大値 + 1。
未反映分を含めないと、2 つの申請が同じコードを取ってしまう。

それでも衝突したときは、反映時に「そのコードが既にある」と検知して
**その明細を完了にしない**（管理者が差し戻して、申請者に取り直してもらう）。

### 落ちたときの状態

各明細は独立している。途中で落ちても、落ちた明細は `PENDING`/`READY` のまま残る。
ヘッダが `APPLIED` にならないので検知できる。再実行は同じ明細を「完了」にするだけ。

`$batch` の各サブリクエストの `Content-Length` は **UTF-8 バイト長**で計算する。
JS の `.length`（UTF-16 コード単位）だと日本語を含む body で SharePoint が途中で切って 400 になる。

## 7. 件数としきい値

`PRM_Grants` がいちばん伸びる。**利用者数 × 所属組織区分1数 × 権限6種**が上限。

例: 利用者 500 人 / 平均 1.2 組織区分1 / 平均 2 権限 ≒ 1,200 行。
全員が全権限を持つ最悪ケースで 3,600 行。**5,000 行のしきい値には収まる想定。**

ただし `PRM_RequestItems` は**消さずに積む**ので、いずれ 5,000 を超える。

- `ReqNo` / `EntityKey` / `SubmittedAt` に索引を張る（索引列でのフィルタはしきい値を超えても効く）
- 一覧は必ず期間または対象で絞ってから取得する。全件取得の画面を作らない
- 超えたら年度別リストへの分割を検討（`PRM_RequestItems_2026` 等）

## 8. Entra ID（AD）からの取り込み

`Office365Users` は**標準コネクタ**。Premium なしで使える。

| 欲しい情報 | AD 属性 | 取れるか |
|---|---|---|
| 氏名 | `displayName` | ○ |
| メールアドレス | `mail` | ○ |
| 部署名 | `department` | ○ |
| 役職 | `jobTitle` | ○ |
| 事業所 | `officeLocation` | ○ |
| グローバルID | `employeeId` 等 | **要確認**（下記） |
| 組織区分1 への所属 | — | **たぶん引けない**（下記） |

### 方針: AD は入力補助、マスタは焼き込み

**AD を都度参照するのではなく、申請時に引いた値をマスタに保存する。** 理由は 4 つ。

1. **履歴が壊れる。** これがいちばん重い。申請書に「部署名: 情報システム部」と残っているのに、
   その人が異動したら過去の申請書の部署名まで変わってしまう。
   **申請当時の姿を残せない**なら履歴の意味がない
2. **退職者が消える。** AD から消えた人の権限履歴は残す必要がある
3. **一覧が実用にならない。** ギャラリーの各行で `Office365Users.UserProfileV2()` を呼ぶと、
   **行数分の API 呼び出し**が走る。数百行で体感できないほど遅くなり、スロットリングにも当たる
4. **絞り込めない。** AD の属性で SharePoint リストをフィルタすることはできない（結合が無い）。
   「情報システム部の人の権限一覧」は、部署名をマスタに持っていないと出せない

### 使いどころ

```
利用者登録申請の画面だけで AD を叩く:
  Office365Users.SearchUserV2({searchTerm: txtSearch.Text}).value
    → 候補を出す
    → 選んだら 氏名 / メール / 部署名 を入力欄に自動セット（編集可）
    → 申請確定時に PRM_Users へ焼き込む
```

**一覧・権限画面では AD を一切呼ばない。** マスタだけ読む。

### 定期的な差分チェックが要る

焼き込む以上、**マスタは放っておくと古くなる**。異動・改姓・退職が反映されない。

- 棚卸し画面を作り、`PRM_Users` の各行と AD を突き合わせて差分を出す
- 差分の反映は**申請として通す**（`ReqType = USER`、`ApplicantName` に「AD 同期」）。
  黙って書き換えると、いつ変わったかが履歴から消える
- AD に居ない人は `IsActive = false` にする。**行は消さない**（権限履歴の参照先が消える）

### グローバルID は AD に無い（確定）

**AD からは引けないので、利用者登録申請で手入力する。**

これは「AD から引いた人」と「入力されたグローバルID」が**同一人物である保証が無い**ことを意味する。
仕組みで防げないので、次の 3 つで受け止める。

1. **一意制約**（`Title`）で二重登録だけは止める
2. **形式チェック**をクライアント側で入れる（桁数・文字種。**規則の確認が必要**）
3. **確認画面で並べて見せる。** 「グローバルID / 氏名 / メール / 部署」を 1 画面に出して
   申請者に目視確認させる。自動で通さない

`AdObjectId` を併せて保存するので、**AD 側の同一性はそちらで担保する**。
グローバルID の誤りは、あとから棚卸しで「同じ人が 2 つのグローバルIDで登録されている」
（= 同じ `AdObjectId` が 2 行）として検出できる。**この検査はリストに入れておく。**

### 組織区分1 への所属は手で選ぶ（確定）

**`department`（部署名）と 組織区分1 は別物。** 組織区分1 は事業場相当の独自コード体系で、
AD の部署名はもっと細かい単位。自動では対応しない。

利用者登録申請で、申請者が組織区分1 を選択する。

- 選択肢は `PRM_Org1`（`IsActive = true`）の全件。AD による絞り込みはしない
- **複数所属をそのまま扱える。** `PRM_UserOrg1` に行を足すだけ
- **入力ミスは機械的に検出できない。** 承認フローを入れるまでは申請者の責任になる。
  確認画面で「氏名 / 部署名（AD） / 選んだ組織区分1」を並べ、
  部署名と組織区分1 が食い違っていないか人が見て気付ける形にしておく

所属を外すときは `IsActive = false`。**行は消さない。**
その組織区分1 の権限が宙に浮くので、仕様書 §7 のとおり確認画面で影響件数を出す。

## 9. 初期データ投入

マスタは CSV / Excel からの一括投入を想定。

- 組織区分1 → 組織区分2 の順（親が無いと `Org1Code` が宙に浮く）
- 利用者 → 所属 → 権限 の順
- 投入も**申請として記録する**（`ReqType = ORG1` などで 1 申請にまとめ、`ApplicantName` に「初期投入」）

初期投入だけ履歴を残さないと、**「最初からこうだった」のか「誰かが入れた」のかが区別できなくなる。**

# 権限仕様

IT セキュリティ関連の担当者権限を、組織区分に対して付与・変更するための仕様。

> 作業名 `permhub` は仮。正式名称が決まったら差し替える。

---

## 1. 登場するもの

| # | 名前 | 説明 | 申請対象 |
|---|---|---|---|
| 1 | 組織区分1 | 上位の組織単位（事業場相当） | マスタ変更申請 |
| 2 | 組織区分2 | 組織区分1の配下の組織単位 | マスタ変更申請 |
| 3 | 利用者 | 権限を持つ人 | 利用者登録申請 |
| 4 | 所属 | 利用者がどの組織区分1に属するか | 利用者登録申請 |
| 5 | 権限 | 利用者 × 組織区分1 × 権限種類 | 権限変更申請 |

組織区分1・組織区分2 は**あらかじめマスタ登録されているものから選択**する。
権限申請の中でマスタを新規作成することはない（マスタ変更は別の申請）。

## 2. 組織区分1

| 項目 | 内容 |
|---|---|
| コード | **申請者は記入しない**（採番または管理者設定） |
| 表示順 | 一覧の並び順 |
| 日本語名称 | |
| 英語名称 | |
| 多段階設定要否 | **利用申請種別ごとに 要 / 不要**（後述） |

### 多段階設定要否

**「この組織区分1では、その利用申請種別について多段階承認の設定を行うか」** を決めるフラグ。
利用申請種別は次の 3 つで、それぞれ独立に 要 / 不要 を持つ。

- 外部接続申請
- 無線LAN申請
- クラウド申請

**不要にした種別は、配下の組織区分2 の「多段階承認要否」が意味を持たなくなる。**

---

## 3. 組織区分2

| 項目 | 内容 |
|---|---|
| コード | **申請者は記入しない** |
| 親の組織区分1 | どの組織区分1の配下か |
| 表示順 | |
| 日本語名称 | |
| 英語名称 | |
| 多段階承認要否 | **利用申請種別ごとに 要 / 不要** |

### 多段階承認要否

**「この組織区分2は、その利用申請種別の多段階承認の対象か」**。
組織区分1 と同じ 3 種別それぞれに 要 / 不要 を持つ。

### 有効な多段階承認（判定式）

組織区分1 と組織区分2 の **両方が「要」のときだけ有効**。

```
有効(組織区分2, 種別) = 親組織区分1.多段階設定要否[種別] = 要
                     かつ 組織区分2.多段階承認要否[種別] = 要
```

この「有効」が、後述の**組織区分2 の選択可否**を決める。

> 組織区分1 が「不要」なら、組織区分2 側で「要」にしていても有効にならない。
> マスタ画面では、組織区分1 が不要の種別は組織区分2 側の入力を無効化（グレーアウト）して混乱を防ぐ。

## 4. 利用者

| 項目 | 内容 | 取得元 |
|---|---|---|
| グローバルID | **一意キー**。変わらない前提 | **手入力**（AD には無い） |
| 氏名 | | AD `displayName` |
| メールアドレス | 変わりうるのでキーにしない | AD `mail` |
| 部署名 | | AD `department` |
| ADオブジェクトID | AD 突合用の副キー。画面には出さない | AD `id` |

**AD（Entra ID）は「入力補助」であって「参照先」ではない。**
申請時に AD から引いて、**その時点の値をマスタに焼き込む**。
理由は [data-model.md](data-model.md) の「Entra ID からの取り込み」を参照。

### グローバルID の形式

次のどちらか。**手入力なので入力チェックを必ず入れる。**

- 数字 7 桁 — `1234567`
- 先頭がアルファベット 1 文字 + 数字 6 桁 — `A123456`

```
IsMatch(txtGid.Text, "^([0-9]{7}|[A-Za-z][0-9]{6})$")
```

アルファベットの大文字小文字は**保存時に大文字へ寄せる**（`Upper()`）。
`a123456` と `A123456` が別人として二重登録されるのを防ぐ。

### 所属

利用者は**あらかじめ組織区分1に割り当てられている**。
権限を付与するとき、担当者は**その組織区分1に割り当て済みの利用者の中からのみ選択**できる。

1 人の利用者が複数の組織区分1 に所属してよい。

### 所属は「最新」と「当時」を使い分ける

| 用途 | 使う値 | 出どころ |
|---|---|---|
| **画面のアクセス制御**（自分が見られる組織区分1） | **最新** | `PRM_UserOrg1`（現行値） |
| **一覧・詳細の表示** | **最新** | 同上 |
| **申請書を後から読む** | **申請当時** | `PRM_RequestItems` の焼き込み |

申請者が自分の所属組織の登録情報を見るときは**常に最新**。
異動して所属が変わったら、その日から新しい組織区分1 が見えて古い方は見えなくなる。

一方、過去の申請書を開いたときは**当時の所属・当時の部署名**で表示する。
現行値を参照してしまうと、異動のたびに過去の申請書の中身が書き換わる。

## 5. 権限

### 5.1 権限の種類（6 種）

| コード | 名称 | 権限種別（正/副） |
|---|---|---|
| `SECMGR` | 事業場ITセキュリティ責任者権限 | なし |
| `CONFORM` | 適合化担当権限 | なし |
| `EXTCONN` | 外部接続申請担当権限 | **あり** |
| `WLAN` | 無線LAN申請担当権限 | **あり** |
| `CLOUD` | クラウド申請担当権限 | **あり** |
| `INFOSEC` | 情報セキュリティ担当権限 | なし |

### 5.2 付与の単位

**1 件の権限付与 = 利用者 × 組織区分1 × 権限の種類**

同じ人が、複数の組織区分1 について、それぞれ別の権限を持てる。
同じ組織区分1 の中で複数の権限を持つこともできる。

### 5.3 範囲（スコープ）

6 種すべてが、次の 2 つのどちらかを取る。

| 範囲 | 意味 |
|---|---|
| **全体** | 組織区分1担当として、**その組織区分1配下の組織区分2すべて**に権限を持つ |
| **個別** | 指定した組織区分2（**複数選択可**）にのみ権限を持つ |

### 5.4 個別選択できる組織区分2 の条件

**「有効な多段階承認」（§3）がある組織区分2 のみ選択できる。** どの種別で判定するかは権限によって違う。

| 権限 | 判定に使う利用申請種別 |
|---|---|
| `EXTCONN` 外部接続申請担当 | 外部接続申請 |
| `WLAN` 無線LAN申請担当 | 無線LAN申請 |
| `CLOUD` クラウド申請担当 | クラウド申請 |
| `SECMGR` 事業場ITセキュリティ責任者 | **3 種別のいずれか 1 つでも有効** |
| `CONFORM` 適合化担当 | **3 種別のいずれか 1 つでも有効** |
| `INFOSEC` 情報セキュリティ担当 | **3 種別のいずれか 1 つでも有効** |

条件を満たさない組織区分2 は**選択肢に出さない**（グレーで出して選べなくするのではなく、そもそも並べない）。

> **注意:** マスタ変更で組織区分2 が「不要」に変わると、**既に付与済みの権限が条件を満たさなくなる**ことがある。
> §7 の整合性チェックを参照。

### 5.5 権限種別（正 / 副）

`EXTCONN` / `WLAN` / `CLOUD` の 3 権限だけが持つ。

| 値 | |
|---|---|
| 事業会社（正） | |
| 事業会社（副） | |

**権限ごとに別々に設定する。** 同じ人が「外部接続申請担当 = 正、無線LAN申請担当 = 副」を持てる。
付与の単位（§5.2）と同じ粒度なので、権限 1 件につき 1 つの値を持つ。

他の 3 権限では空にする。

## 6. 申請

### 6.1 申請の種類

| 種別 | 対象 | 内容 |
|---|---|---|
| 組織区分1マスタ変更 | 組織区分1 | 追加 / 変更 / 削除 |
| 組織区分2マスタ変更 | 組織区分2 | 追加 / 変更 / 削除 |
| 利用者登録 | 利用者・所属 | 追加 / 変更 / 削除 |
| 権限変更 | 権限 | 追加 / 変更 / 削除 |

### 6.2 履歴の要件

**マスタ変更・権限変更のどちらも、「申請単位で申請内容をあとから追える」こと。**

そのために:

- **1 申請 = 1 ヘッダ + 複数明細**。明細 1 件が 1 エンティティの変更に対応する
- 明細には**変更前と変更後の値を両方**残す
- 現在の状態は別テーブルで持つ（履歴を毎回たどらない）

「いつ・誰が・何を・どう変えたか」が、申請番号から一続きで読める状態にする。

詳細は [data-model.md](data-model.md)。

## 7. 整合性チェック（運用上の注意）

マスタが変わると、既存の権限が仕様に合わなくなることがある。**申請時の検証だけでは防げない。**

| きっかけ | 起きること | 対応 |
|---|---|---|
| 組織区分1 の多段階設定要否を 要 → 不要 | 配下の組織区分2 が全種別で無効になり、個別指定の権限が宙に浮く | マスタ変更申請の確認画面で影響件数を出す |
| 組織区分2 の多段階承認要否を 要 → 不要 | その組織区分2 を個別指定していた権限が条件違反になる | 同上 |
| 組織区分2 の削除 | 個別指定に存在しないコードが残る | 同上。削除時は参照件数を出して警告 |
| 利用者の所属解除 | その組織区分1 の権限が宙に浮く | 所属解除時に権限も一緒に失効させるか確認 |

**方針:** 既存権限を自動で書き換えない。**申請の確認画面で影響を提示し、申請者に判断させる。**
勝手に消すと、権限が消えた理由が履歴から追えなくなる。

## 8. 仮決めした点（要確認）

実装前に潰しておきたいもの。

| # | 仮決めした内容 | 確認したいこと |
|---|---|---|
| 1 | **「全体」は多段階承認要否に関係なく配下すべて** | 「組織区分1担当として」と書かれているので組織区分1全体の権限と解釈した。全体でも有効な組織区分2に限る、なら変更が必要 |
| 2 | 利用者マスタ自体の登録も申請対象に含める | 人事データ連携などで自動投入されるなら申請から外す |
| 3 | グローバルID を利用者の一意キーとする | 変わりうるならキーを別に立てる |
| 3b | **グローバルID の形式（桁数・文字種）** | 手入力になるので入力チェックを入れたい。規則を教えてほしい |
| 4 | 承認フローは今回のスコープ外 | 申請＝即反映。状態列は用意しておく |
| 5 | 組織区分2 の個別指定は同一組織区分1 の配下に限る | 組織区分1 をまたいだ指定は不可としている |

# 画面設計

[spec-permission.md](spec-permission.md) / [data-model.md](data-model.md) の前提。
モック: `permhub-mock.html`（3タブ + 利用者詳細 + 申請詳細）

## 1. 画面構成

**画面は 3 つ。うちホームが 3 タブ。**

| 画面 | 中身 |
|---|---|
| `ScrHome` | 組織区分1 セレクタ + **3 タブ**（組織マスタ / ユーザマスタ / 申請履歴） |
| `ScrUser` | 利用者の登録・変更・削除（基本情報・所属・権限） |
| `ScrReq` | 申請の詳細。一覧と同じ 4 操作を申請まるごとに掛けられる |

```
┌──────────────────────────────────────────────┐
│ ユーザ権限申請                 検証 太郎     │  ヘッダ
├──────────────────────────────────────────────┤
│  組織マスタ │ ユーザマスタ │ 申請履歴        │  タブ
├──────────────────────────────────────────────┤
│ 組織区分1 [東日本ブロック ▼]                 │  組織/ユーザタブ内のセレクタ
└──────────────────────────────────────────────┘
```

### 組織区分1 セレクタは各タブの中に置く

セレクタは **組織マスタ / ユーザマスタ タブの中**（タブ直下・コンテンツ先頭）に出す。
「その組織区分1 のマスタを設定する」「その組織区分1 のメンバー権限を見る」という
タブの作業対象を、そのタブの中で選ばせる。**申請履歴タブには出さない**
（履歴は直前に選んでいた組織区分1 の申請を表示する）。

- セレクタは 1 つの `ModernDropdown` を `Visible = gblTab = "org" || gblTab = "user"` で出し分ける
  （選んだ値 `gblOrg1` は 3 タブすべてに効く。実体が 1 つなのでタブ間で選択が保たれる）
- 選択肢は**自分が利用者登録されている組織区分1 のみ**
- 所属が 1 件しかない人にはドロップダウンを出さず、名称をラベルで出すだけにする

### 初期表示は「ユーザマスタ」タブ

日常的に開くのは権限の確認なので、マスタ設定ではなくマトリックスから始める。

## 2. 組織マスタ タブ

**組織区分1 の設定**と**組織区分2 の設定**を縦に 2 枚のカードで並べる。

```
┌ 組織区分1 の設定 ────────────────────────────────────┐
│ コード B01(変更不可) 日本語名称[ ] 英語名称[ ] 表示順[ ]│
│ 多段階設定要否                                        │
│  外部接続[要|不要] 無線LAN[要|不要] クラウド[要|不要] │
│                        [組織区分1 の変更を申請]       │
└───────────────────────────────────────────────────────┘
┌ 組織区分2 の設定                        [+ 新規登録] ┐
│コード│日本語名称 │英語名称 │表示順│  多段階承認要否   │
│      │           │         │      │外部接続│無線│雲 │
│A0101 │[北海道支店]│[Hokkaido]│ [1] │[要|不要]│…  │…  │
│A0102 │[東北支店] │[Tohoku] │ [2] │[要|不要]│…  │…  │
│              n件の組織区分2 を表示中 [組織区分2 の変更を申請]│
└───────────────────────────────────────────────────────┘
```

### 組織区分2 は「行 = 組織区分2、列 = 設定項目」の表にする

1 件ずつ選んで別ペインで設定する形にしない。**全件が一度に見えて、その場で直せる**方が速い。
多段階承認要否は 3 種別が横に並ぶので、組織区分2 どうしの設定差が一目で分かる。

### 申請ボタンは画面に 1 つ（組織マスタ・ユーザマスタ共通）

**組織マスタ タブとユーザマスタ タブで同じ `btnSubmitAll` を出す。**
どちらのタブで押しても、**未申請の変更をすべて**まとめて申請する。

> 組織区分2 を足してから権限を付けたいのに、マスタ側の申請が反映されるまで
> ユーザマスタで触れない——という往復をなくすため。マトリックスは
> **編集中のマスタ**（`colO2Edit`）を見るので、申請前でも新しい組織区分2 に権限を付けられる（§19）。

ボタンのラベルは `申請（n件）`。n は **組織区分1 の要否 + 組織区分2 の変更行 + 権限の変更**の合計
（`fChgAllN`）。位置だけタブで変える（`Y: =If(gblTab = "org", …-106, …-86)`）。

**書き込まれる申請は種別ごとに分かれる。**

| 変更したもの | 作られる申請 |
|---|---|
| 組織区分1 の多段階設定要否 | `ORG1` 1 件 |
| 組織区分2 の要否・表示順 | `ORG2` 1 件（変更した行がすべて明細に入る） |
| 権限（マトリックス） | `GRANT` 1 件 |

3 つとも変えていれば 1 クリックで 3 件の申請が立ち、
通知は `申請しました（REQ-…-4812、REQ-…-9915）` のように**全部の申請番号**を並べる。
承認者が種別で違うので、**申請そのものは混ぜない**（1 本にすると片方だけ差し戻せない）。

**組織区分2 側は「変更した行だけ」をまとめて 1 申請にする。**
1 行ずつ申請させると、6 件直すのに 6 申請になって履歴が読みにくい。
1 申請の中に複数の `ORG2` 明細が入る形（[data-model.md](data-model.md) の明細設計そのまま）。

実装は 1 本の `OnSelect` に 3 セクションを並べたもの。**セクションごとに実行フラグ
（`gblGo1` / `gblGo2` / `gblGo3`）を持たせて**、変更のない種別は丸ごと飛ばす。
`Select()` で 3 つのボタンを順に叩く形にしなかったのは、`gblReqNo` が
互いに上書きされる危険があるため（1 本の式なら `;` の順に評価される）。

### 親が「不要」の種別は入力させない

組織区分1 の多段階設定要否が「不要」の種別は、組織区分2 側で「要」にしても
[有効にならない](spec-permission.md)。要/不要のボタンを出さず **`― 設定不可`** と表示し、
表の下に**どの種別がなぜ設定できないか**を書く。

グレーアウトだけだと理由が分からず、権限を付けられない原因を探し回ることになる。

### コードは変更不可

`Title` がキーで `PRM_Org2.Org1Code` や `PRM_Grants.Org2Codes` から参照されている。
**変えると参照が全部切れる。** 読み取り専用にする。
新規追加時のコードは申請者に入力させず**採番する**（仕様上「申請者は記入しない」）。

### 組織区分2 の追加と削除（実装済み）

**追加**は「＋ 新規登録」でモーダルを開き、日本語名称・英語名称だけを入力する。

- **申請するまでコードは「未割当」と表示する。** 採番規則は運用側で決まっていないので、
  申請者に見せる意味がない。一覧もマトリックスも `未割当` と出す
- 実際のコードは**登録の瞬間**に `"A" & 組織区分1コードの下2桁 & 連番2桁`（`B01` → `A0107`）で採番する。
  **無効化済みの行も含めた最大値+1** にする（`colO2Any`）。使い回すと `Title` の一意制約に当たる
- 追加した行は編集コレクション（`colO2Edit`）に `IsNew` 付きで入り、一覧に `● 新規` で出る。
  **申請前でもユーザマスタのマトリックスに出る**ので、そのまま権限を付けて 1 回で申請できる
- 多段階承認の要否は追加後に一覧で設定する（初期値はすべて 不要 ＝ 権限を付けられない状態）

**削除**は行の「削除」ボタン。`IsDel` を立てるだけで、押した時点では消えない。

- 一覧では名称が赤 + `● 削除` になり、ボタンが「取消」に変わる（申請前なら戻せる）
- **追加した行の削除は行ごと消す**（申請していないので履歴に残す意味がない）
- **削除する組織区分2 に個別指定の権限が残っていると申請できない**（§19）。
  マトリックス側では削除マークの行が「対象外」になり、残った権限が赤いセルで出る

申請時の明細は `Operation` で `ADD` / `UPDATE` / `DELETE` を分け、
`PRM_Org2` へは 追加＝新規レコード、削除＝`IsActive = false`、変更＝該当列の更新 を書く。

### 名称は一覧でそのまま直す（実装済み）

日本語名称・英語名称は**表の中がテキスト入力**になっていて、その場で書き換えられる
（`OnChange` で編集コレクションに `Patch`）。削除マークの行は入力できない（`DisplayMode.View`）。

- 変更した行には `● 未申請` が付き、`申請` にまとまる（要否・表示順と同じ 1 つの `ORG2` 明細）
- `ChangeText` は差分だけを並べる:
  `東北支社（A0102）：日本語名称 東北支店→東北支社`
- **コードは変更できない**（`Title` がキーで、権限の `Org2Codes` から参照されている）

## 3. ユーザマスタ タブ — 権限マトリックス

**行 = 組織区分2、列 = メンバー、セル = 権限の有無。権限種別でビューを切り替える。**

```
権限種別 [事業場IT責任者][適合化][外部接続][無線LAN][クラウド][情シス]
                          ~~~~~~~~                    [+ 新規登録]
                                               ◀ 1-10/12人 ▶
┌──────────────┬───────┬───────┬───────┬───────┐
│組織区分2     │検証太郎│山田花子│●佐藤一郎│鈴木次郎│
│              │       │ 副    │ 正    │       │
├──────────────┼───────┼───────┼───────┼───────┤
│全体(組織区分2すべて)│  ☑   │  ☐   │  ☐   │  ☑   │
├──────────────┼───────┼───────┼───────┼───────┤
│北海道支店 A0101│  ☑   │  ☐   │  ☑   │  ☑   │
│東北支店   A0102│  ☑   │  ☐   │  ☑   │  ☑   │
│関東支店   A0103│  ―   │  ―   │  ―   │  ―   │
└──────────────┴───────┴───────┴───────┴───────┘
 ☑ 権限あり  ☐ 権限なし  ― 対象外  ● = 未申請の変更あり
                              [権限の変更を申請（1件）]
```

### セルの意味

| 表示 | 意味 |
|---|---|
| `☑`（緑） | この組織区分2 に権限がある（全体権限 or 個別指定） |
| `☐` | 権限なし |
| `―`（グレー） | **対象外**。選択中の権限種別で[有効な多段階承認](spec-permission.md)が無い |
| `☑`（赤・セルも赤） | **対象外なのに個別指定が残っている**（§19）。外すまで申請できない |

**「権限なし」と「対象外」を分けるのが要。** どちらも空欄にすると、
権限を付け忘れているのか、そもそも付けられないのかが読めない。

全体権限（`ScopeType = ALL`）か個別指定（`PICK`）かは**「全体」行**で見る。
セル側は「効いているかどうか」だけを見せる。

### セルをクリックすると権限が変わる（申請前の下書き）

| 操作 | 結果 |
|---|---|
| 組織区分2 のセル | その組織区分2 だけを付与／削除 |
| 「全体」のセル | 全体権限を付与（＝対象の組織区分2 すべてに ☑）／すべて削除 |
| 全体が ☑ の状態で組織区分2 を外す | 全体が ☐ になり、外した 1 つだけが ☐ になる |
| 対象の組織区分2 が全部 ☑ になった | 全体が自動で ☑（＝ `ScopeType` が `ALL` に戻る） |

多段階設定が無効な組織区分1 では、組織区分2 の行はすべて `―` で「全体」だけが押せる。

クリックは `colGEdit`（下書き）だけを書き換え、**SharePoint には触らない**。
変更のある利用者は氏名に `●` が付き、フッタのボタンが
「権限の変更を申請（N件）」になる。押すと `PRM_Requests` / `PRM_RequestItems` /
`PRM_Grants` をまとめて書く。

> マトリックスから新規に作られた権限は **正副（`CompanyRole`）が空**になる。
> 正/副が要る権限は利用者詳細で設定する。

### 正/副は列ヘッダに出す

権限種別（正/副）は **利用者 × 組織区分1 × 権限** の単位で、組織区分2 ごとには変わらない。
セルに毎行書くと同じ文字が縦に並ぶだけ。列ヘッダに 氏名 / グローバルID / 正・副 を積む。
`EXTCONN` / `WLAN` / `CLOUD` のビューのときだけ正副を出す。

### ビュー切り替えは 6 ボタン

ドロップダウンにしない。6 つしかなく、比べながら行き来する使い方なので 1 クリックの方が速い。

### 絞り込みは付けない

誰に権限が無いかを見るのがマトリックスの目的なので、既定で絞ると抜けが見えない。
「権限のある人だけ表示」トグルは置いていたが**実装が無い**まま残っていたので外した
（必要になったら、列を作る 736 箇所すべてで同じ絞り込み式を使う必要がある）。

### 横方向はスクロールではなくページング（10 人ずつ）

各行が独立に横スクロールすると、行ごとに見ている列がずれて**マトリックスとして読めなくなる**。
Power Apps では複数ギャラリーのスクロール位置を同期できない。
列幅が固定されるのでヘッダとセルの位置合わせも壊れない。

**列はコントロールをベタ書きしている**（`mhN1..10` / `mhOpen1..10` / `mxA1..10` / `mxC1..10` と
`fG1..fG10`）。動的に列を増やせないので、1 ページの人数を変えるときは
名前付き数式の `fPage` と、この 4 系統のコントロール、ページャの計算を揃えて直す。

| | 幅 |
|---|---|
| 組織区分2 の名前 + コード | 150 + 58 = 208 |
| 1 列 | 105 × 10 = 1050 |
| 行の合計 | 1258（1366px 幅で縦スクロールバーぶんの余白が残る） |

ヘッダと「全体」行は**画面に絶対配置**（X = 252 + (n-1) × 105）、
組織区分2 の行だけがギャラリーの中にある。横スクロールを付けるにはこの 3 つを
1 つの横スクロールコンテナーにまとめ直す必要があり、**組織区分2 の名前列も一緒に流れる**
（名前列だけ固定するには 2 つのギャラリーの縦スクロールを同期させる必要があり、これはできない）。

### 詳細への導線

**列ヘッダの氏名をクリックすると `ScrUser`（変更モード）へ。**
行そのものには遷移を付けない。セルはクリックすると権限が変わるので、
画面遷移と編集が同じクリックにならないよう**遷移は氏名だけ**にしている。

## 4. 申請履歴 タブ

**選択中の組織区分1 に関わる申請を、種別を問わず 1 つの一覧に並べる。**
管理者はここが作業画面も兼ねる（専用の管理タブは置かない）。

```
申請の種別 [すべて][組織マスタ変更][ユーザ・権限申請]
状態      [すべて][申請済み][確認中][完了][差し戻し][取り下げ]   41件（未完了 2）
┌────────┬──────────┬────────┬────────┬──────┬────┬──┬──────┬──────────────┐
│申請日時│申請番号  │種別    │組織区分1│対象  │申請者│明細│状態  │操作          │
│…07:13  │REQ-…-957 │組織＋ユーザ│東日本 │東日本│検証…│ 1 │申請済み│[確認中][完了][差し戻し][取り下げ]│
└────────┴──────────┴────────┴────────┴──────┴────┴──┴──────┴──────────────┘
        行をクリック（操作列より左）すると申請の詳細へ
        差し戻し・取り下げは理由が必須（空だと実行できない）
```

### 種別 × 状態の 2 段フィルタ

種別と状態は **AND** で効く。どちらも「すべて」が既定。

| 状態チップ | 含める `Status` |
|---|---|
| 申請済み | `SUBMITTED` |
| 確認中 | `INPROGRESS` / `PARTIAL` |
| 完了 | `APPLIED` |
| 差し戻し | `REJECTED` |
| 取り下げ | `CANCELED` |

「一部完了」（`PARTIAL`）は**確認中に含める**。まだ全部が片付いていない＝人が見る必要がある、
という運用上の意味では同じ箱でよい。行の状態表示は「一部完了」のまま出す。

### 管理者は全組織区分1 を見る

申請者は選択中の組織区分1 の申請だけ。**管理者は組織区分1 セレクタを無視して全件**を出す。
専用タブを廃して申請履歴に統合したので、ここで守備範囲を絞ると他組織の申請が捌けなくなる。

どちらのモードで見ているかは、件数の上に常に文字で出す。

### 行からの操作

| ボタン | 誰に出るか | 対象になる明細 | マスタ |
|---|---|---|---|
| 確認中 | 管理者・`SUBMITTED`/`PARTIAL` のとき | `PENDING` の明細 | 触らない |
| 完了 | 管理者・完了/取り下げ以外 | `DONE` 以外の明細 | **書き込む**（確認モーダル） |
| 差し戻し | 管理者・差し戻し/完了/取り下げ以外 | `DONE` 以外の明細 | 触らない（**理由必須**モーダル） |
| 取り下げ | **申請者本人**・`SUBMITTED` のとき | 全明細 | 触らない（**理由必須**モーダル） |

取り下げを「本人・未着手のうちだけ」に絞ってあるので、管理者が作業を始めた後に
足元をすくわれることがない。

操作は**申請まるごと**が対象。詳細画面（`ScrReq`）にも同じ 4 つを置いてあり、
どちらから押しても同じ処理が動く（§5）。

### 操作ボタンは固定幅のコンテナに入れる

AutoLayout は `Visible = false` の子を**詰めて**並べるので、ボタンの出し分けを
そのまま並べると**行ごとに列位置がずれる**。ボタン 4 つを固定幅（238）の
コンテナで包み、その中で出し分ける。ヘッダも同じ幅の AutoLayout で組んで、
絶対座標での位置合わせをやめる。

## 5. `ScrReq` — 申請の詳細と作業

申請者は参照だけ。管理者にだけ作業ボタンが出る（取り下げは申請者本人に出る）。

```
┌ 申請の詳細 ───────────────────────────────────────┐
│ 申請番号 REQ-…  申請種別 組織＋ユーザ  対象 東日本 │
│ 申請日時 …  状態 申請済み  明細件数 3  組織区分1 …│
└───────────────────────────────────────────────────┘
[組織マスタの変更（2）][ユーザマスタの変更（1）]
                  [確認中にする][完了にする][差し戻す][取り下げる]
┌───────────────────────────────────────────────────┐
│ # │操作│対象種別  │対象      │変更内容                    │
│ 1 │追加│組織区分2 │A0108     │…新規登録                   │
│ 2 │変更│組織区分1 │B01       │…外部接続 要→不要           │
│ 3 │追加│権限      │A234567#…│…権限なし→個別（差し戻し理由）│
└───────────────────────────────────────────────────┘
```

### サブ切り替えで組織マスタ／ユーザマスタを分ける

1 申請に両方の変更が混ざるので、**担当が違う作業を混ぜて並べない**。

| サブタブ | `EntityKind` |
|---|---|
| 組織マスタの変更 | `ORG1` / `ORG2` |
| ユーザマスタの変更 | `USER` / `USERORG1` / `GRANT` |

画面を開いたときは**中身のある側**を自動で選ぶ（組織側が 0 件ならユーザ側）。

### 状態は申請まるごとで動かす

明細ごとに状態を変えられるようにしていたが、**運用の単位が申請 1 本**なので外した。
明細の行から状態列と作業ボタンが消え、操作は上の 4 つだけになっている。

- `ItemStatus` は列としては残す（`PENDING`/`READY`/`DONE`/`REJECTED`/`CANCELED`）。
  申請の状態はこれの集計（[data-model.md](data-model.md) §6）なので、
  申請単位で押しても全明細に同じ値が入るだけ
- 一覧（`ScrHome`）と詳細（`ScrReq`）に同じ 4 つを置く。押した先は同じ処理
- **完了は元に戻せない**（マスタに書くので）。全ボタンが確認モーダルを挟む
- 差し戻しからは完了に戻せる（誤操作の逃げ道）。完了と取り下げからは動かせない

### 差し戻し・取り下げは理由を必須にする

理由なしで差し戻されると申請者が何を直せばいいか分からない。取り下げも、
後から履歴を見たときに「なぜ引っ込めたのか」が残らないと監査に使えない。

- 理由が空のあいだは実行ボタンを**グレーのまま**にし、押しても
  `Notify("理由を入力してください。")` で止める（`IsBlank(Trim(inpRRej.Text))`）
- 理由は `gblRejNote` に入れて `ItemNote` に書く。`REJECTED` と `CANCELED` の**両方**で書く
- モーダルの見出し・例文・ボタン文言は `gblHAct`（`done`/`rej`/`cxl`）で切り替える

### 反映は「完了」の副作用

完了にした時点で `AfterJson` をマスタに当てる（[data-model.md](data-model.md) §6）。
処理は 1 か所（[`src/Apply.Item.txt`](../src/Apply.Item.txt)）に書いて、
`ScrHome`・`ScrReq` それぞれの隠しボタンに**同じ内容を貼る**。
画面をまたいで `Select()` できないための複製なので、
**片方だけ直すと今回のように取り下げ理由が落ちる**。直すときは必ず両方に貼り直す。

変更前・変更後は**申請した時点の値**を表示する（明細に焼き込んだもの）。
現行値を参照すると、マスタが改名されるたびに過去の申請書が書き換わる。

## 6. `ScrUser` — 利用者の登録・変更・削除

```
[変更申請] 既存ユーザの情報と権限を変更します
┌ 基本情報 ─────────────────────────────────────────┐
│ グローバルID[2345678] 氏名[佐藤 一郎]             │
│ メール[…] 部署名[生産技術部]        [ADから取得]  │
└───────────────────────────────────────────────────┘
┌ 所属組織区分1 と権限 ─────────────────────────────┐
│ [東日本ブロック][中部ブロック][+ 所属を追加]      │
│ ┌─権限──────────┬─設定──────────────────────┐  │
│ │☑ 事業場ITセキュ │ 範囲 [全体][個別]           │  │
│ │☐ 適合化担当     │                             │  │
│ │☑ 外部接続申請   │ 組織区分2                   │  │
│ │☐ 無線LAN申請    │  ☑北海道支店 ☐東北支店     │  │
│ └─────────────────┴─────────────────────────────┘  │
│          [キャンセル] [この内容で申請]            │
└───────────────────────────────────────────────────┘
```

### 所属組織区分1 は「タブ」にする

3 ペイン（所属 / 権限 / 設定）にすると 1366px で各 420px しか取れず、
組織区分2 のチェックボックスが 2 列に並ばない。
**所属を横並びのタブにして、下を 2 ペインにする。** 所属が複数ある人は多くない。

### 基本情報の変更（実装済み）

氏名・メールアドレス・部署名を書き換えて `変更を申請` を押すと、
**権限の変更とは別に `USER` の申請が 1 本立つ**（明細は `UPDATE` 1 件）。

- ボタンの件数は **基本情報の変更（1件）＋ 権限の変更の件数**
- 権限だけ・基本情報だけ・両方、どれでも押せる（両方なら `USER` と `GRANT` の 2 申請）
- `ChangeText` は変わった項目だけ:
  `佐藤 一郎（2345678）：部署名 生産技術部→生産技術第二部`
- 氏名を空にしては申請できない
- 反映後は `PRM_Users` を読み直してマトリックスの氏名にも即反映する

### 新規登録（実装済み）

`＋ 新規登録` から入ると **新規申請モード**（`gblUserMode = "New"`）になる。

- 所属組織区分1 は**ドロップダウンで 1 つ選ぶ**（申請者が所属している組織区分1 のみ）。
  タブは既存利用者の所属を出すものなので、新規では隠す
- 権限はそのまま付けられる。編集コレクションには `Gid = ""` の行として溜まり、
  登録時に入力されたグローバルIDで書き直す
- ボタンは `この内容で登録を申請`

**1 つの `USER` 申請に 3 種別の明細**が入る（§5 の設計どおり）。

| Seq | 対象種別 | 内容 |
|---|---|---|
| 1 | `USER` | 利用者を登録（氏名・メール・部署） |
| 2 | `USERORG1` | 所属を追加（`<グローバルID>#<組織区分1>`） |
| 3.. | `GRANT` | 付けた権限のぶんだけ |

書き込みは `PRM_Users` / `PRM_UserOrg1` / `PRM_Grants` の 3 本。
検証は **グローバルIDの形式・重複・氏名・所属**の 4 つ。

### 編集コレクションの upsert に `IsBlank(<キー列>)` を使わない

```
NG: If(IsBlank(gblUG.Gid), Collect(colGEdit, {...}), Patch(colGEdit, ..., {...}))
OK: If(CountRows(Filter(colGEdit, Gid = gblUserGid && O1 = gblUserOrg1 && Role = gblUserRole)) = 0, Collect(...), Patch(...))
```

**キーが空文字のときに「行が無い」と誤判定する。** 新規登録の画面はグローバルIDが空なので、
チェックを入れるたびに `Collect` が走って行が増え続け、
**一度付けたチェックが外せない**（表示は最初の行を見ているので常に ☑ のまま）。
実際に 42 行たまった。存在判定は必ず `CountRows(Filter(...)) = 0` で行う。

### グローバルID

- **新規のときだけ編集可。** 変更・削除では読み取り専用（キーなので変えられない）
- 形式チェック `^([0-9]{7}|[A-Za-z][0-9]{6})$`、保存時に `Upper()`
- 重複チェックは申請ボタン押下時

### 「ADから取得」

- `Office365Users.SearchUserV2()` で候補を出し、選ぶと 氏名 / メール / 部署名 / AdObjectId が入る
- 入った後も**編集可**にする。AD が古い場合に直せないと詰む
- **AD を叩くのはこのボタンだけ。** 一覧やマトリックスでは呼ばない

### 組織区分2 のチェックリスト

**「有効な多段階承認」がある組織区分2 だけ並べる**（[仕様 §5.4](spec-permission.md)）。
判定に使う種別は選択中の権限で変わる。条件を満たさないものは**そもそも出さない**。
何件隠したかはコールアウトで示す。

**既に付与済みなのに条件を満たさなくなった組織区分2 は、警告付きで表示する。**
黙って消すと、申請したら権限が減っていた、という事故になる。

## 7. 申請の単位

**1 回の申請 = 1 レコード。** 組織マスタの変更と権限の変更が混ざってよい。

| 画面 | 申請ボタン | 明細に入る `EntityKind` |
|---|---|---|
| `ScrHome`（組織マスタ / ユーザマスタ） | 1 つ | `ORG1` / `ORG2` / `GRANT` |
| `ScrUser`（変更） | 1 つ | `USER` / `GRANT` |
| `ScrUser`（新規登録） | 1 つ | `USER` / `USERORG1` / `GRANT` |
| `ScrUser`（削除） | 「この利用者を削除」 | `USER` / `USERORG1` / `GRANT` |

`ReqType` は変更内容から自動判定する（複数種別が混ざったら `MIXED`）。
履歴一覧の種別チップを意味のあるものに保つためで、処理の分岐には使わない
（処理は明細の `EntityKind` で分岐する）。

申請番号は `REQ-yyyymmdd-hhmmss-<乱数3桁>`。`Title` に一意制約があるので、
採番したあと存在チェックし、当たっていたら枝番を付ける。

## 8. アプリの操作権限（保留）

**最終的には、この仕組みの `PRM_Users` に登録されている人だけが利用できるようにする。**

いまは**保留**。当面は「その組織区分1 に所属していれば参照も申請もできる」で作る。

```
起動時:
  gblMyAdId = Office365Users.MyProfileV2().id
  gblMe     = LookUp(PRM_Users, AdObjectId = gblMyAdId)
  colMyOrg1 = Filter(PRM_UserOrg1, GlobalId = gblMe.Title, IsActive = true)
```

- **ログイン者の特定はメールではなく `AdObjectId` で行う。** メールは改姓・転籍で変わる
- `gblMe` が空 = 利用者未登録 → **本実装ではここで弾く**。当面は警告表示にとどめる
- `colMyOrg1` が空 = 所属なし → 同上

**閲覧のみ / 管理者といった役割分けは未定。** 後から足すと全画面のアクセス制御に触ることになるので、
本番運用の前に決める。

## 9. 実装上の注意（Power Apps）

- **ギャラリーは全部レイアウトコンテナー（`GroupContainer` / `AutoLayout`）に入れる。**
  入れないと貼り付けのたびに `Y` がずれ、透明な板として入力欄を覆う
- **タブは `Visible` の切り替えで作る。** コンテナーごと出し入れする
- `ModernTextInput` の読み取りは `.Text`（`.Value` ではない）
- `If()` の分岐に `;` 連結を書くと最初の式しか実行されない
- **`Office365Users` の呼び出しはギャラリーの中に置かない。** 行数分の API 呼び出しになる
- 委任: `PRM_UserOrg1` / `PRM_Grants` は `GlobalId` `Org1Code` で絞る（索引済み）。
  `PRM_RequestItems` は必ず `ReqNo` / `EntityKey` / 期間で絞ってから取得する

### マトリックスは「行=ギャラリー / 列=固定コントロール」で作る（実機検証済み）

**ネストギャラリーも `WrapCount` 平坦化も動かなかった。** 通ったのは次の形だけ。

```
galMx.Items = Sort(Filter(colOrg2All, Org1Code = gblOrg1), SortOrder)   ← 実在のリストレコード
  mxRow（横方向 AutoLayout コンテナー）
    mxRowName / mxRowCode / mxC1 .. mxC8   ← 列ぶんの固定セル
```

行は組織区分2 の**実レコード**なので `ThisItem.NameJa` / `ThisItem.Title` が普通に解決する。
可変なのは「どのメンバーがその列か」だけなので、それはセルの数式側で解く。

```
mxC3.Text =
  If(IsBlank(Index(<ページ内メンバー>, 3).GlobalId), "",
  If(!(<この行が対象かの判定>), "―",
  If(IsBlank(<その人の権限>.GlobalId), "",
  If(<その人の権限>.ScopeType.Value = "ALL", "◎",
  If(";" & ThisItem.Title & ";" in <その人の権限>.Org2Codes, "○", "")))))
```

#### 試して駄目だった順

1. ネストギャラリー → 内側の子が `ThisItem.Mark` を解決しない
2. `WrapCount` で平坦化 → セルが描画されない
3. `AddColumns` で結合 → 派生列が子で解決しない
4. **固定列 → 成功**

原因は一貫して「**`AddColumns` / `ForAll` で作った派生列がギャラリーの子で解決しない**」。
行を実レコードにすればこの制約に触れない。

#### セルは AutoLayout で並べる（絶対 X は使わない）

ギャラリー テンプレート内の子の `X` は**貼り付け時に黙って書き換えられる**。
これで一度、5〜8 列目が重なって**別人の権限が隣の列に表示されていた**。
行を横方向 AutoLayout のコンテナーにして、子に `X` を持たせないこと。
詳細と再現条件は [powerapps-controls.md](powerapps-controls.md)。

#### 位置合わせ

列見出し（`mhN1..8` / `mhR1..8` / `mhOpen1..8`）は**画面レベルの固定コントロール**。
セル幅を固定値（130px）にしてあるので、見出しの `X` も `252 + n * 130` で決め打ちにする。
**セル幅を `FillPortions` の等分にすると行幅の揺れで見出しとずれる**ので、固定値にする。

#### 残る制約

- **列は 8 固定。** `◀ ▶` で 8 人ずつページングする。列を増やすにはコントロールを足す
- 組織区分2 が表示領域に収まらない場合は行側もページングか絞り込みが要る（未確定 §10-6）

## 11. 組織区分2 の要否を画面で変更する（実装済み）

組織マスタ タブの「多段階承認要否」（外部接続 / 無線LAN / クラウド）は、
**セルをクリックすると 要 ⇄ 不要 が切り替わる。** 変更はその場では保存されず、
「組織区分2 の変更を申請」を押したときにまとめて申請として記録・反映される。

### 編集用のコレクションを分ける

`colOrg2All`（保存済み）と `colO2Edit`（編集中）の 2 本を持つ。

| コレクション | 中身 | 使う場所 |
|---|---|---|
| `colOrg2All` | SharePoint の現在値 | マトリックスの判定、変更の有無の比較元 |
| `colO2Edit` | 編集中の値 | 組織マスタ タブの一覧（`galO2.Items`） |

**この 2 本を分けないと、未申請の変更がマトリックスの権限判定に紛れ込む。**
一覧は `colO2Edit` を、マトリックスは `colOrg2All` を見る。

> `galO2.Items` を `colOrg2All` のままにすると、トグルしても表示が変わらない
> （件数だけ増える）。実際にこれを一度やった。

セルの `OnSelect`:

```
If(LookUp(colOrg1, Title = gblOrg1).MsExt,
   Patch(colO2Edit, LookUp(colO2Edit, Title = ThisItem.Title), {ApExt:!ThisItem.ApExt}))
```

`If` で囲うことで、**組織区分1 側が「不要」の種別（`―` 表示）はクリックしても何も起きない**。

### 未申請の変更を見せる

`colO2Edit` と `colOrg2All` を比べて、変わっているセルに枠線、行末に「● 未申請」を出す。
申請ボタンには件数を出し、0 件のときはグレーにする。

### 申請時（`btnO2Submit.OnSelect`）

1. 変更行を `colO2Chg` に抽出（変更前 / 変更後の両方を持たせる）
2. 0 件なら警告して終了
3. `PRM_Requests` にヘッダ（`ReqType = ORG2`）
4. `PRM_RequestItems` に明細（`ForAll(Sequence(...))` で連番を振る）
5. **`PRM_Org2` を実際に更新**
6. ヘッダを `APPLIED` に
7. `colOrg2All` を取り直し、`colO2Edit` を作り直す

> 権限変更の申請（`Submit.Grant.txt`）は申請の記録だけで `PRM_Grants` を更新しないが、
> **こちらは 5 でマスタを実際に更新する。** 承認フローが入るまでの暫定。

### 整合性チェック（仕様 §7）を申請前に出す

**要 → 不要 にすると、その組織区分2 を個別指定していた既存権限が条件を満たさなくなる。**
仕様どおり**自動では書き換えず、申請前に影響を提示する**。

表の下の説明文が、影響があるときだけ警告に変わる。

```
⚠ この変更で 1 件の既存権限が対象外になります（佐藤 一郎（外部接続申請担当））。
   権限は自動では消されません。申請後に個別に見直してください。
```

申請ボタンの文言も「影響を承知して申請」に変わる。

#### 判定

「変更後に対象外」かつ「**変更前は有効だった**」ものだけを数える。
前者だけだと、もともと条件を満たしていない権限（過去の不整合）まで並んで警告が読めなくなる。

```
対象 = ScopeType = "PICK" かつ Org2Codes にそのコードを含む権限
Bad  = 変更前に有効(colOrg1 + colOrg2All) かつ 変更後に無効(colO1Edit + colO2Edit)
```

判定に使う種別は権限で変わる（仕様 §5.4）。
`EXTCONN`/`WLAN`/`CLOUD` は対応する 1 種別、
`SECMGR`/`CONFORM`/`INFOSEC` は **3 種別のいずれか 1 つでも有効なら有効**。

> 実機で確認: `A0102` を個別指定している権限は 5 件あるが、外部接続だけを不要にしたとき
> 警告に出るのは外部接続申請担当の 1 件だけ。無線LAN 担当・クラウド担当・
> 適合化担当・情報セキュリティ担当は他の種別が「要」のまま有効なので出ない。

### 組織区分1 の要否も同じ形で変更できる

`colO1Edit` を編集用に持ち、`ReqType = ORG1` として申請する。

**組織区分2 側のガードは `colO1Edit`（編集中）を見る。**
組織区分1 を「不要」にした瞬間、組織区分2 の該当列が全行 `―` に変わり、
**連鎖する影響がその場で見える**。保存済みの `colOrg1` を見ると、
申請するまで影響が分からない。

`PRM_Org1` を更新したあとは `gblP1` も取り直す（マトリックスの判定に使っているため）。

## 12. 権限をマトリックスから変更する（実装済み）

組織マスタの要否編集（§11）と同じ「編集用コレクション + まとめて申請」の形。

### コレクションと名前付き数式

| コレクション | 中身 | 使う場所 |
|---|---|---|
| `colGrantsAll` | `PRM_Grants` の現在値（レコードそのまま） | 変更の有無の比較元 |
| `colGEdit` | `{Gid, O1, Role, Scope, Codes, CR}` に畳んだ編集中の値 | マトリックスの表示・クリック |
| `colReq` | 選択中の組織区分1 の申請（`PRM_Requests`） | 申請履歴タブ |

マトリックスが参照する式は**すべて `App.Formulas`（名前付き数式）に括り出してある**。
セルに直接書くと 1 セルにつき 20 回ほどコレクションを走査することになり、操作できないほど重くなる。

| 名前付き数式 | 中身 |
|---|---|
| `fMem` / `fPage` | 選択中の組織区分1 のメンバー / そのうち現在ページの 8 人 |
| `fG1`〜`fG8` | 各列のグローバルID（人数が足りない列は `""`） |
| `fP1` | 選択中の組織区分1 のレコード（多段階設定要否の判定に使う） |
| `fOrg2` | 選択中の組織区分1 の組織区分2（表示順） |
| `fChg` | `colGEdit` と `colGrantsAll` の差分（未申請の変更） |
| `fBad` | 要否の変更で対象外になる既存権限（仕様§7 の整合性チェック） |
| `fHist` | 申請履歴（`colReq` を種別トグルで絞ったもの） |

`fBad` は組織マスタ タブの警告文とボタン 3 つが同じ式を 9 回書いていたもの。
`ForAll(権限) × ForAll(組織区分2)` の二重ループなので、括り出す前は
**組織マスタ タブを見ていなくても**毎レンダリング 9 回走っていた
（Power Apps は非表示コントロールのプロパティも評価する）。


`colGEdit` は `PRM_Grants` を**平らな文字列だけのレコード**に畳んである。
選択肢列（`RoleCode` / `ScopeType` / `CompanyRole`）は `.Value` を取り出して入れる。
ギャラリーの子から選択肢列をたどると解決しないことがあるため。

### 「全体」と組織区分2 の連動

クリックのたびに新しい `Codes` を作り、**対象の組織区分2 を何個含むかで `Scope` を決め直す**。

```
n = 対象の組織区分2 のうち Codes に入っている数
n = 0            → Scope = "NONE"（Codes は空にする）
n = 対象すべて   → Scope = "ALL" （Codes は空にする）
それ以外         → Scope = "PICK"
```

`ALL` と `NONE` のときに `Codes` を空にするのが要。残しておくと、
あとから対象の組織区分2 が増えたときに「全体のはずが一部だけ」になる。

### 申請の書き込み

`btnGrantSubmit` が `colGEdit` と `colGrantsAll` を突き合わせて `colGChg`（差分）を作り、

1. `PRM_Requests` に 1 件（`ReqType = GRANT`）
2. `PRM_RequestItems` に差分の数だけ（`ADD` / `UPDATE` / `DELETE`）
3. `PRM_Grants` を upsert（`Scope = NONE` は `IsActive = false` の論理削除）

の順で書き、最後に `colGrantsAll` / `colGEdit` を取り直す。

`Operation` は変更前後の `Scope` で決める（`NONE → 何か` = `ADD`、
`何か → NONE` = `DELETE`、それ以外 = `UPDATE`）。

> 実機で確認: 権限なし→全体 が `ADD` / `{"ScopeType":"ALL"}`、
> 個別（東北支店）→個別（北海道支店、東北支店） が `UPDATE` /
> `{"ScopeType":"PICK","Org2Codes":";A0102;A0101;"}` として記録され、
> `PRM_Grants` の `CompanyRole` は保持された。

## 16. 利用者詳細からの権限変更（実装済み）

マトリックスと**同じ `colGEdit` を編集する**ので、どちらの画面で直しても
`● 未申請` マーカーと件数は一致する。違いは申請の切り口だけ。

| 画面 | 申請の単位 |
|---|---|
| ユーザマスタのマトリックス | **選択中の組織区分1 の、全利用者**の変更 |
| 利用者詳細 | **その利用者の、全組織区分1**の変更 |

### 範囲はマトリックスと同じチェックボックスで表す

左の権限リストのチェックは**表示だけ**。付与・削除は右のチェックボックスで行う。

```
権限の範囲（クリックで付与・削除／― は多段階承認が無効で設定できない）
 ☑ 全体(組織区分2すべて)
 ───────────────────────────────────
 ☑ 北海道支店      ☑ 東北支店
 ☑ 関東支店        ― 甲信越支店
 ☐ 北関東事業所    ☐ 東京第一事業所
```

**「なし / 全体 / 個別」の 3 択トグルは廃止した。** 個別で組織区分2 を選んだあとに
「なし」を押すと選択が全部消え、押し間違いの取り返しがつかない。
マトリックスと同じ「チェックを外していく」操作なら、状態は 1 つずつしか動かない。

| 画面の状態 | `PRM_Grants` |
|---|---|
| 全体 が ☑ | `ScopeType = ALL`、`Org2Codes` は空 |
| 組織区分2 の一部が ☑ | `ScopeType = PICK`、☑ の組織区分2 が `Org2Codes` |
| すべて ☐ | `ScopeType = NONE` → 申請時に `IsActive = false`（論理削除） |

- 全体の ☑ を外すと**すべて ☐（＝権限なし）**になる。マトリックスの「全体のセル」と同じ
- 対象の組織区分2 を全部チェックすると自動で `ALL` に戻る（マトリックスと同じ正規化）
- **一覧は全件出す。** 仕様§5.4 で対象外の組織区分2 は `―`（グレー）にして
  クリックを受け付けない。対象の組織区分2 だけを出す作りにすると、
  「無いのか、対象外なのか」がここでも読めなくなる
- チェックボックスの大きさ・記号・色はマトリックスと揃える

## 17. 利用者の削除（実装済み）

削除は**論理削除**で、**所属と権限を連鎖して失効させる**。
`PRM_Users.IsActive` だけを落とすとマトリックスの列は `PRM_UserOrg1` 由来なので
利用者が残り続け、氏名だけが空になる。

```
PRM_Users.IsActive     = false
PRM_UserOrg1.IsActive  = false   （その利用者の所属すべて）
PRM_Grants.IsActive    = false   （その利用者の権限すべて。LastReqNo も記録）
```

`ReqType = USER` の申請として記録し、明細は**利用者 1 件 + 失効した権限の数**。
誤操作を防ぐため**確認モーダルを 1 枚挟む**（§18）。

> 実機で確認: 削除後にマトリックスから当人が消え（12人→11人）、
> `PRM_Users` / `PRM_UserOrg1` / `PRM_Grants` がすべて `IsActive = false` になり、
> 申請明細が「利用者を無効化」＋失効した権限 2 件で記録された。

## 15. 表示順は ▲▼ で入れ替える（実装済み）

キャンバスアプリのギャラリーに**行のドラッグ＆ドロップ並べ替えは無い**（PCF が要るが、
このテナントでは PCF を有効にできない）。代わりに各行の `表示順` の右に **▲▼** を置き、
**隣の行と `SortOrder` を交換**する。

```
Set(gblSwapA, ThisItem.Title);
Set(gblSwapB, Coalesce(Last(Filter(fO2E, SortOrder < ThisItem.SortOrder)).Title, ThisItem.Title));
Set(gblSwapN, ThisItem.SortOrder);
Set(gblSwapM, LookUp(colO2Edit, Title = gblSwapB).SortOrder);
Patch(colO2Edit, LookUp(colO2Edit, Title = gblSwapA), {SortOrder:gblSwapM});
Patch(colO2Edit, LookUp(colO2Edit, Title = gblSwapB), {SortOrder:gblSwapN})
```

- **隣が無いときは自分自身を相手にする**（`Coalesce(..., ThisItem.Title)`）。
  こうすると同じ値を入れ直すだけの空振りになり、`If` で分岐せずに済む。
  存在しないレコードを `Patch` の第2引数に渡す形を作らないための書き方
- 先頭行の ▲ / 末尾行の ▼ はグレーにする。**AutoLayout では非表示にすると桁が詰まる**ので
  `Visible` は使わず `Color` と `Fill` で落とす
- ギャラリーの `Items` は `fO2E`（`SortOrder` で並べ替え済み）なので、交換した瞬間に並び替わる

### 並べ替えも申請の対象

`SortOrder` の変更は要否の変更と同じ 1 つの `ORG2` 申請にまとまる。

- `● 未申請` マーカーと申請ボタンの件数は**要否と表示順の両方**を見る
- `BeforeJson` / `AfterJson` に `SortOrder` を含める
- `ChangeText` は両方あるとき「クラウド 不要→要、表示順 2→1」のように連結する

> 実機で確認: 表示順のみ（2件）、要否＋表示順の同一行（`「北海道支店（A0101）：クラウド
> 不要→要、表示順 2→1」`）のいずれも `PRM_Requests` / `PRM_RequestItems` / `PRM_Org2`
> に正しく書かれ、一覧が即座に並び替わることを確認した。

## 18. 承認者がいなくなる警告（実装済み）

多段階承認が有効な組織区分2 は、**その権限を持つ人が 1 人もいなくなると申請を承認できなくなる**。
権限の削除・範囲の縮小・利用者の削除で簡単に起こるので、次の 2 段構えで気づけるようにした。

| | 出るもの | 場所 |
|---|---|---|
| **常時表示** | `⚠ 承認できる人がいない組み合わせが n 件あります（組織区分2／権限種別…）` | ユーザマスタ タブの下端、利用者詳細の下端 |
| **申請の直前** | 確認モーダル（取消 / 承知して申請） | 権限の変更を申請・変更を申請・この利用者を削除 |

- 常時表示は**編集中の `colGEdit` を見る**ので、セルをクリックした瞬間に出る／消える。
  申請を反映したあとも状態が残っていれば出たままになる（＝「今まさに欠けている」の表示）
- **止めない。** 「反映しても構いませんが、その組織区分2 では申請を承認できる人がいなくなります」と
  伝えるだけで、承知して押せば通す。組織の実態として一時的に空になることはあるので塞がない
- 判定は仕様§5.4 と同じ資格判定を通した組み合わせだけを数える。
  多段階承認が無効な組織区分2（`―` のセル）は数えない

### 実装

名前付き数式に「欠ける組み合わせ」を 3 通り用意して、画面はそれを参照するだけにした。

| 数式 | 何を仮定するか |
|---|---|
| `fNoApp` / `fNoAppN` / `fNoAppTxt` | 選択中の組織区分1（マトリックスの編集後） |
| `fNoAppU` / `fNoAppUN` / `fNoAppUTxt` | 利用者詳細で開いている組織区分1（同じく編集後） |
| `fNoAppDel` / `fNoAppDelN` / `fNoAppDelTxt` | **その利用者の権限を全部除いた**状態（削除の予測） |

モーダルは 1 組のコントロール（`mdlBg`/`mdlCard`/`mdlTitle`/`mdlBody`/`mdlNote`/`mdlCancel`/`mdlOk`）で、
`gblModal` が `"grant"` か `"del"` かで文言と OK ボタンのラベルを切り替える。

```
btnGrantSubmit.OnSelect:
  ... ClearCollect(colGChg, fChg);
  If(IsBlank(gblErr) && fNoAppN > 0 && !gblGateOk, Set(gblStop, true));
  If(gblStop, Set(gblModal, "grant")); Set(gblGateOk, false);
  If(IsBlank(gblErr) && !gblStop, ...)   ← 以降の書き込みは全部 && !gblStop

mdlOk.OnSelect:
  Set(gblGateOk, true); Set(gblModal, ""); Select(btnGrantSubmit)
```

- **`Select(コントロール)` で本体を呼び直す**ので、申請の本体を 2 か所に書かなくて済む。
  `gblGateOk` は入口で必ず `false` に戻す（次回また確認が出る）
- モーダルのコントロールは**画面の子の一番最後**に置く。手前にあると
  オーバーレイの上に元のボタンが残り、暗くならないうえに押せてしまう
- 一覧に出す組み合わせの連結は `Concat(テーブル, 式, "、")` の**第3引数（区切り）**を使う。
  式の末尾に `& "、"` を足すと末尾に余分な「、」が残る

### キャンセルは編集を捨てる

利用者詳細の **キャンセル / 一覧へ戻る は `colGEdit` を `colGrantsAll` から作り直す**。
これをやらないと、申請せずに戻ったのにマトリックス側に `● 未申請` と件数が残る
（編集コレクションは画面ではなくアプリに属しているため）。

> 実機で確認: 適合化担当の「全体」を 1 つ外すと赤字が即座に出て、申請ボタンで
> モーダル → 取消では書かれず、承知して申請で `REQ-20260725-3118` が記録された。
> 利用者詳細でも同じ組み合わせで赤字とモーダルが出て、削除モーダルは
> **その利用者を除いた場合の 2 件**を挙げた。キャンセルで編集が破棄されることも確認した。

## 19. 多段階承認を外したときに宙に浮く権限（実装済み）

組織マスタで多段階承認要否を **要 → 不要** にすると、その組織区分2 を**個別指定**していた権限は
効かなくなる。従来はマトリックスがその組み合わせを `―`（対象外）で描くだけだったので、
**残ったままの個別指定が画面から見えなかった**。

### 赤いセルで見せて、外すまで申請を通さない

| | 挙動 |
|---|---|
| ユーザマスタのマトリックス | 対象外なのに個別指定が残っているセルを **赤い ☑ ＋ 赤い背景**で出す。クリックで外せる |
| 利用者詳細の組織区分2 | 同じく **赤い ☑ ＋ 赤い名称**。クリックで外せる |
| リストの下 | `⚠ 多段階承認が無効になった組織区分2 に権限が n 件残っています。赤いセルをクリックして外してください（氏名（権限種別）…）` |
| 申請ボタン | 押すと**エラーを出して止まる**（承認できる人がいない警告と違い、モーダルで押し切れない） |

- **判定は編集中の組織マスタ（`colO1Edit` / `colO2Edit`）で行う。**
  組織マスタ タブで要否を落とした瞬間に、まだ申請していなくてもマトリックスに赤が出る。
  組織マスタの申請 → ユーザマスタで後始末、という順序でも、逆でも同じ表示になる
- そのため**マトリックスの `―` も編集後のマスタに従う**（`galMx.Items` は `fO2E`）。
  組織マスタ タブと表示順・要否がずれない
- **「全体」は赤くしない。** 仕様上「全体」は多段階承認要否に関係なく組織区分1 配下すべてなので、
  組織区分2 側の要否を落としても無効にならない。赤くするのは**個別指定（PICK）だけ**
- 組織マスタ側の申請は従来どおり**止めない**（§7 の警告のみ）。
  権限の後始末を先にやらせると、要否を落とせないまま詰むため
- ただし**組織区分2 の削除だけは止める**。削除は参照先ごと消えるので、
  権限を残したまま通すと画面から直せなくなる（削除マークの行は「対象外」として数える）
- **ブロックの判定に「権限の変更があるか」を混ぜない。** 混ぜると
  「組織区分2 を削除するだけ」の申請がすり抜ける（実際にすり抜けた）

### 実装

```
fEligM  = Filter(fO2E, <§5.4 の資格判定（fO1E と gblView）>)   ← 編集後のマスタで有効な組織区分2
fEligMC = Concat(fEligM, ";" & Title, "") & ";"                ← セルの判定は文字列の in で1回
fInv    = 組織区分1 内の PICK 権限のうち、資格の無いコードを持つもの
fInvN   = Sum(fInv, Bad)      fInvTxt = Concat(fInv, Nm, "、")
fInvU / fInvUN                ← 利用者詳細用（その利用者の全所属）
```

- セル 16 個ぶんの資格判定を `fEligMC` の `in` に置き換えたので、式も短くなり再計算も 1 回で済む
- 赤いセルのクリックは**外す方向にしか効かない**。トグルの新しいコード列は
  `fEligM`（資格のあるものだけ）から組み立て直すので、資格の無いコードは自然に落ちる
- 警告が出ると一覧の高さを 26px 縮める（`cntMx.Height` に `If(fInvN > 0, 26, 0)`）。
  絶対配置のラベルを増やすと**下のコントロールと重なる**ので、出し入れで高さを調整する

> 実機で確認: 東北支店の外部接続を 要→不要 にすると、その瞬間にマトリックスの
> 山田 花子・佐藤 一郎のセルが赤くなり、下に警告が出て、申請ボタンがエラーで止まった。
> 赤いセルを 2 つ外すと警告が消えて申請できる状態に戻った。利用者詳細でも同じ表示になり、
> 赤いチェックを外すと `個別 3件 → 2件` になった（いずれも SharePoint への書き込みなし）。

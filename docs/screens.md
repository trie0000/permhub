モック: `permhub-mock.html`（3タブ + 利用者詳細 + 申請詳細）

## 1. 画面構成

**画面は 3 つ。うちホームが 3 タブ。**

| 画面 | 中身 |
|---|---|
| `ScrHome` | 組織区分1 セレクタ + **3 タブ**（組織マスタ / ユーザマスタ / 申請履歴） |
| `ScrUser` | 利用者の登録・変更・削除（基本情報・所属・権限） |
| `ScrReq` | 申請の詳細（参照専用） |

```
┌──────────────────────────────────────────────┐
│ ユーザ権限申請                 検証 太郎     │  ヘッダ
├──────────────────────────────────────────────┤
│  組織マスタ │ ユーザマスタ │ 申請履歴        │  タブ
├──────────────────────────────────────────────┤
│ 組織区分1 [東日本ブロック ▼]                 │  組織/ユーザタブ内のセレクタ
└──────────────────────────────────────────────┘
```

### 組織区分1 セレクタは各タブの中に置く

セレクタは **組織マスタ / ユーザマスタ タブの中**（タブ直下・コンテンツ先頭）に出す。
「その組織区分1 のマスタを設定する」「その組織区分1 のメンバー権限を見る」という
タブの作業対象を、そのタブの中で選ばせる。**申請履歴タブには出さない**
（履歴は直前に選んでいた組織区分1 の申請を表示する）。

- セレクタは 1 つの `ModernDropdown` を `Visible = gblTab = "org" || gblTab = "user"` で出し分ける
  （選んだ値 `gblOrg1` は 3 タブすべてに効く。実体が 1 つなのでタブ間で選択が保たれる）
- 選択肢は**自分が利用者登録されている組織区分1 のみ**
- 所属が 1 件しかない人にはドロップダウンを出さず、名称をラベルで出すだけにする

### 初期表示は「ユーザマスタ」タブ

日常的に開くのは権限の確認なので、マスタ設定ではなくマトリックスから始める。

## 2. 組織マスタ タブ

**組織区分1 の設定**と**組織区分2 の設定**を縦に 2 枚のカードで並べる。

```
┌ 組織区分1 の設定 ────────────────────────────────────┐
│ コード B01(変更不可) 日本語名称[ ] 英語名称[ ] 表示順[ ]│
│ 多段階設定要否                                        │
│  外部接続[要|不要] 無線LAN[要|不要] クラウド[要|不要] │
│                        [組織区分1 の変更を申請]       │
└───────────────────────────────────────────────────────┘
┌ 組織区分2 の設定                        [+ 新規登録] ┐
│コード│日本語名称 │英語名称 │表示順│  多段階承認要否   │
│      │           │         │      │外部接続│無線│雲 │
│A0101 │[北海道支店]│[Hokkaido]│ [1] │[要|不要]│…  │…  │
│A0102 │[東北支店] │[Tohoku] │ [2] │[要|不要]│…  │…  │
│              n件の組織区分2 を表示中 [組織区分2 の変更を申請]│
└───────────────────────────────────────────────────────┘
```

### 組織区分2 は「行 = 組織区分2、列 = 設定項目」の表にする

1 件ずつ選んで別ペインで設定する形にしない。**全件が一度に見えて、その場で直せる**方が速い。
多段階承認要否は 3 種別が横に並ぶので、組織区分2 どうしの設定差が一目で分かる。

### 申請ボタンは 2 つ

組織区分1 の変更と組織区分2 の変更は**別の申請種別**（`ORG1` / `ORG2`）なので分ける。

**組織区分2 側は「変更した行だけ」をまとめて 1 申請にする。**
1 行ずつ申請させると、6 件直すのに 6 申請になって履歴が読みにくい。
1 申請の中に複数の `ORG2` 明細が入る形（[data-model.md](data-model.md) の明細設計そのまま）。

### 親が「不要」の種別は入力させない

組織区分1 の多段階設定要否が「不要」の種別は、組織区分2 側で「要」にしても
[有効にならない](spec-permission.md)。要/不要のボタンを出さず **`― 設定不可`** と表示し、
表の下に**どの種別がなぜ設定できないか**を書く。

グレーアウトだけだと理由が分からず、権限を付けられない原因を探し回ることになる。

### コードは変更不可

`Title` がキーで `PRM_Org2.Org1Code` や `PRM_Grants.Org2Codes` から参照されている。
**変えると参照が全部切れる。** 読み取り専用にする。
新規追加時のコードは申請者に入力させず**採番する**（仕様上「申請者は記入しない」）。

## 3. ユーザマスタ タブ — 権限マトリックス

**行 = 組織区分2、列 = メンバー、セル = 権限の有無。権限種別でビューを切り替える。**

```
権限種別 [事業場IT責任者][適合化][外部接続][無線LAN][クラウド][情シス]
                          ~~~~~~~~                    [+ 新規登録]
                                               ◀ 1-8/12人 ▶
┌──────────────┬───────┬───────┬───────┬───────┐
│組織区分2     │検証太郎│山田花子│●佐藤一郎│鈴木次郎│
│              │       │ 副    │ 正    │       │
├──────────────┼───────┼───────┼───────┼───────┤
│全体（配下すべて）│  ☑   │  ☐   │  ☐   │  ☑   │
├──────────────┼───────┼───────┼───────┼───────┤
│北海道支店 A0101│  ☑   │  ☐   │  ☑   │  ☑   │
│東北支店   A0102│  ☑   │  ☐   │  ☑   │  ☑   │
│関東支店   A0103│  ―   │  ―   │  ―   │  ―   │
└──────────────┴───────┴───────┴───────┴───────┘
 ☑ 権限あり  ☐ 権限なし  ― 対象外  ● = 未申請の変更あり
                              [権限の変更を申請（1件）]
```

### セルの意味

| 表示 | 意味 |
|---|---|
| `☑` | この組織区分2 に権限がある（全体権限 or 個別指定） |
| `☐` | 権限なし |
| `―`（グレー） | **対象外**。選択中の権限種別で[有効な多段階承認](spec-permission.md)が無い |

**「権限なし」と「対象外」を分けるのが要。** どちらも空欄にすると、
権限を付け忘れているのか、そもそも付けられないのかが読めない。

全体権限（`ScopeType = ALL`）か個別指定（`PICK`）かは**「全体」行**で見る。
セル側は「効いているかどうか」だけを見せる。

### セルをクリックすると権限が変わる（申請前の下書き）

| 操作 | 結果 |
|---|---|
| 組織区分2 のセル | その組織区分2 だけを付与／削除 |
| 「全体」のセル | 全体権限を付与（＝対象の組織区分2 すべてに ☑）／すべて削除 |
| 全体が ☑ の状態で組織区分2 を外す | 全体が ☐ になり、外した 1 つだけが ☐ になる |
| 対象の組織区分2 が全部 ☑ になった | 全体が自動で ☑（＝ `ScopeType` が `ALL` に戻る） |

多段階設定が無効な組織区分1 では、組織区分2 の行はすべて `―` で「全体」だけが押せる。

クリックは `colGEdit`（下書き）だけを書き換え、**SharePoint には触らない**。
変更のある利用者は氏名に `●` が付き、フッタのボタンが
「権限の変更を申請（N件）」になる。押すと `PRM_Requests` / `PRM_RequestItems` /
`PRM_Grants` をまとめて書く。

> マトリックスから新規に作られた権限は **正副（`CompanyRole`）が空**になる。
> 正/副が要る権限は利用者詳細で設定する。

### 正/副は列ヘッダに出す

権限種別（正/副）は **利用者 × 組織区分1 × 権限** の単位で、組織区分2 ごとには変わらない。
セルに毎行書くと同じ文字が縦に並ぶだけ。列ヘッダに 氏名 / グローバルID / 正・副 を積む。
`EXTCONN` / `WLAN` / `CLOUD` のビューのときだけ正副を出す。

### ビュー切り替えは 6 ボタン

ドロップダウンにしない。6 つしかなく、比べながら行き来する使い方なので 1 クリックの方が速い。

### 絞り込みは付けない

誰に権限が無いかを見るのがマトリックスの目的なので、既定で絞ると抜けが見えない。
「権限のある人だけ表示」トグルは置いていたが**実装が無い**まま残っていたので外した
（必要になったら、列を作る 736 箇所すべてで同じ絞り込み式を使う必要がある）。

### 横方向はスクロールではなくページング（8 人ずつ）

各行が独立に横スクロールすると、行ごとに見ている列がずれて**マトリックスとして読めなくなる**。
Power Apps では複数ギャラリーのスクロール位置を同期できない。
列幅が固定されるのでヘッダとセルの位置合わせも壊れない。

### 詳細への導線

**列ヘッダの氏名をクリックすると `ScrUser`（変更モード）へ。**
行そのものには遷移を付けない。セルはクリックすると権限が変わるので、
画面遷移と編集が同じクリックにならないよう**遷移は氏名だけ**にしている。

## 4. 申請履歴 タブ

**選択中の組織区分1 に関わる申請を、種別を問わず 1 つの一覧に並べる。**

```
申請の種別 [すべて][組織マスタ変更][ユーザ・権限申請]        7件
┌──────────────┬───────────────┬────────────┬──────────┬─────┬──┬────┐
│申請日時      │申請番号       │種別        │対象      │申請者│明細│状態│
│2026/07/18 14:22│REQ-…-0007   │権限変更    │佐藤 一郎 │検証…│ 1 │反映済│
│2026/07/16 09:05│REQ-…-0004   │組織区分2マスタ│甲信越支店│山田…│ 1 │反映済│
└──────────────┴───────────────┴────────────┴──────────┴─────┴──┴────┘
                                        行をクリックすると申請の詳細へ
```

**組織マスタ変更もユーザ権限申請も同じ一覧に出す。** どちらも実システムへの反映が必要な申請で、
「いつ何が変わったか」を追うときに種別で分かれていると突き合わせられない。
絞りたいときのために上にフィルタを置く。

一覧には**申請内容を出さない。** 明細件数だけ出して、中身は詳細画面で見る。
1 申請に複数明細が入るので、一覧に展開すると行数が読めなくなる。

## 5. `ScrReq` — 申請の詳細

参照専用。ここから編集はさせない。

```
┌ 申請の詳細 ───────────────────────────────────────┐
│ 申請番号 REQ-…  申請種別 利用者登録  対象 吉田 直樹│
│ 申請者 検証 太郎  申請日時 …  状態 反映済         │
└───────────────────────────────────────────────────┘
┌ 申請内容 ─────────────────────────────────────────┐
│ # │操作│対象種別│対象        │項目      │変更前 → 変更後 │
│ 1 │追加│利用者  │吉田 直樹   │氏名      │（なし）→ 吉田 直樹│
│   │    │        │            │部署名    │（なし）→ 設備管理部│
│ 2 │追加│所属    │…／東日本   │所属      │（なし）→ 東日本ブロック│
│ 3 │追加│権限    │適合化担当  │範囲      │（なし）→ 個別（東京第一）│
└───────────────────────────────────────────────────┘
```

**1 申請に複数の対象種別（利用者 / 所属 / 権限）の明細が入る。**
新規登録では 3 種別が同時に発生するので、これを 1 申請にまとめないと
「1 人登録するのに 3 回申請」になる。

変更前・変更後は**申請した時点の値**を表示する（明細に焼き込んだもの）。
現行値を参照すると、マスタが改名されるたびに過去の申請書が書き換わる。

## 6. `ScrUser` — 利用者の登録・変更・削除

```
[変更申請] 既存ユーザの情報と権限を変更します
┌ 基本情報 ─────────────────────────────────────────┐
│ グローバルID[2345678] 氏名[佐藤 一郎]             │
│ メール[…] 部署名[生産技術部]        [ADから取得]  │
└───────────────────────────────────────────────────┘
┌ 所属組織区分1 と権限 ─────────────────────────────┐
│ [東日本ブロック][中部ブロック][+ 所属を追加]      │
│ ┌─権限──────────┬─設定──────────────────────┐  │
│ │☑ 事業場ITセキュ │ 範囲 [全体][個別]           │  │
│ │☐ 適合化担当     │ 権限種別 [正][副]           │  │
│ │☑ 外部接続申請   │ 組織区分2                   │  │
│ │☐ 無線LAN申請    │  ☑北海道支店 ☐東北支店     │  │
│ └─────────────────┴─────────────────────────────┘  │
│          [キャンセル] [この内容で申請]            │
└───────────────────────────────────────────────────┘
```

### 所属組織区分1 は「タブ」にする

3 ペイン（所属 / 権限 / 設定）にすると 1366px で各 420px しか取れず、
組織区分2 のチェックボックスが 2 列に並ばない。
**所属を横並びのタブにして、下を 2 ペインにする。** 所属が複数ある人は多くない。

### グローバルID

- **新規のときだけ編集可。** 変更・削除では読み取り専用（キーなので変えられない）
- 形式チェック `^([0-9]{7}|[A-Za-z][0-9]{6})$`、保存時に `Upper()`
- 重複チェックは申請ボタン押下時

### 「ADから取得」

- `Office365Users.SearchUserV2()` で候補を出し、選ぶと 氏名 / メール / 部署名 / AdObjectId が入る
- 入った後も**編集可**にする。AD が古い場合に直せないと詰む
- **AD を叩くのはこのボタンだけ。** 一覧やマトリックスでは呼ばない

### 組織区分2 のチェックリスト

**「有効な多段階承認」がある組織区分2 だけ並べる**（[仕様 §5.4](spec-permission.md)）。
判定に使う種別は選択中の権限で変わる。条件を満たさないものは**そもそも出さない**。
何件隠したかはコールアウトで示す。

**既に付与済みなのに条件を満たさなくなった組織区分2 は、警告付きで表示する。**
黙って消すと、申請したら権限が減っていた、という事故になる。

## 7. 申請の単位

| 操作 | `ReqType` | 明細に入る `EntityKind` |
|---|---|---|
| 利用者の登録・変更・削除 | `USER` | `USER` / `USERORG1` / `GRANT` |
| 権限だけの変更 | `GRANT` | `GRANT` |
| 組織区分1 の設定変更 | `ORG1` | `ORG1` |
| 組織区分2 の設定変更・追加（複数行まとめて） | `ORG2` | `ORG2` |

`ScrUser` の申請ボタンは 1 つだが、**変更内容から `ReqType` を自動判定**する。
基本情報も所属も変わらず権限だけ変わったなら `GRANT`、それ以外は `USER`。

## 8. アプリの操作権限（保留）

**最終的には、この仕組みの `PRM_Users` に登録されている人だけが利用できるようにする。**

いまは**保留**。当面は「その組織区分1 に所属していれば参照も申請もできる」で作る。

```
起動時:
  gblMyAdId = Office365Users.MyProfileV2().id
  gblMe     = LookUp(PRM_Users, AdObjectId = gblMyAdId)
  colMyOrg1 = Filter(PRM_UserOrg1, GlobalId = gblMe.Title, IsActive = true)
```

- **ログイン者の特定はメールではなく `AdObjectId` で行う。** メールは改姓・転籍で変わる
- `gblMe` が空 = 利用者未登録 → **本実装ではここで弾く**。当面は警告表示にとどめる
- `colMyOrg1` が空 = 所属なし → 同上

**閲覧のみ / 管理者といった役割分けは未定。** 後から足すと全画面のアクセス制御に触ることになるので、
本番運用の前に決める。

## 9. 実装上の注意（Power Apps）

- **ギャラリーは全部レイアウトコンテナー（`GroupContainer` / `AutoLayout`）に入れる。**
  入れないと貼り付けのたびに `Y` がずれ、透明な板として入力欄を覆う
- **タブは `Visible` の切り替えで作る。** コンテナーごと出し入れする
- `ModernTextInput` の読み取りは `.Text`（`.Value` ではない）
- `If()` の分岐に `;` 連結を書くと最初の式しか実行されない
- **`Office365Users` の呼び出しはギャラリーの中に置かない。** 行数分の API 呼び出しになる
- 委任: `PRM_UserOrg1` / `PRM_Grants` は `GlobalId` `Org1Code` で絞る（索引済み）。
  `PRM_RequestItems` は必ず `ReqNo` / `EntityKey` / 期間で絞ってから取得する

### マトリックスは「行=ギャラリー / 列=固定コントロール」で作る（実機検証済み）

**ネストギャラリーも `WrapCount` 平坦化も動かなかった。** 通ったのは次の形だけ。

```
galMx.Items = Sort(Filter(colOrg2All, Org1Code = gblOrg1), SortOrder)   ← 実在のリストレコード
  mxRow（横方向 AutoLayout コンテナー）
    mxRowName / mxRowCode / mxC1 .. mxC8   ← 列ぶんの固定セル
```

行は組織区分2 の**実レコード**なので `ThisItem.NameJa` / `ThisItem.Title` が普通に解決する。
可変なのは「どのメンバーがその列か」だけなので、それはセルの数式側で解く。

```
mxC3.Text =
  If(IsBlank(Index(<ページ内メンバー>, 3).GlobalId), "",
  If(!(<この行が対象かの判定>), "―",
  If(IsBlank(<その人の権限>.GlobalId), "",
  If(<その人の権限>.ScopeType.Value = "ALL", "◎",
  If(";" & ThisItem.Title & ";" in <その人の権限>.Org2Codes, "○", "")))))
```

#### 試して駄目だった順

1. ネストギャラリー → 内側の子が `ThisItem.Mark` を解決しない
2. `WrapCount` で平坦化 → セルが描画されない
3. `AddColumns` で結合 → 派生列が子で解決しない
4. **固定列 → 成功**

原因は一貫して「**`AddColumns` / `ForAll` で作った派生列がギャラリーの子で解決しない**」。
行を実レコードにすればこの制約に触れない。

#### セルは AutoLayout で並べる（絶対 X は使わない）

ギャラリー テンプレート内の子の `X` は**貼り付け時に黙って書き換えられる**。
これで一度、5〜8 列目が重なって**別人の権限が隣の列に表示されていた**。
行を横方向 AutoLayout のコンテナーにして、子に `X` を持たせないこと。
詳細と再現条件は [powerapps-controls.md](powerapps-controls.md)。

#### 位置合わせ

列見出し（`mhN1..8` / `mhR1..8` / `mhOpen1..8`）は**画面レベルの固定コントロール**。
セル幅を固定値（130px）にしてあるので、見出しの `X` も `252 + n * 130` で決め打ちにする。
**セル幅を `FillPortions` の等分にすると行幅の揺れで見出しとずれる**ので、固定値にする。

#### 残る制約

- **列は 8 固定。** `◀ ▶` で 8 人ずつページングする。列を増やすにはコントロールを足す
- 組織区分2 が表示領域に収まらない場合は行側もページングか絞り込みが要る（未確定 §10-6）

## 11. 組織区分2 の要否を画面で変更する（実装済み）

組織マスタ タブの「多段階承認要否」（外部接続 / 無線LAN / クラウド）は、
**セルをクリックすると 要 ⇄ 不要 が切り替わる。** 変更はその場では保存されず、
「組織区分2 の変更を申請」を押したときにまとめて申請として記録・反映される。

### 編集用のコレクションを分ける

`colOrg2All`（保存済み）と `colO2Edit`（編集中）の 2 本を持つ。

| コレクション | 中身 | 使う場所 |
|---|---|---|
| `colOrg2All` | SharePoint の現在値 | マトリックスの判定、変更の有無の比較元 |
| `colO2Edit` | 編集中の値 | 組織マスタ タブの一覧（`galO2.Items`） |

**この 2 本を分けないと、未申請の変更がマトリックスの権限判定に紛れ込む。**
一覧は `colO2Edit` を、マトリックスは `colOrg2All` を見る。

> `galO2.Items` を `colOrg2All` のままにすると、トグルしても表示が変わらない
> （件数だけ増える）。実際にこれを一度やった。

セルの `OnSelect`:

```
If(LookUp(colOrg1, Title = gblOrg1).MsExt,
   Patch(colO2Edit, LookUp(colO2Edit, Title = ThisItem.Title), {ApExt:!ThisItem.ApExt}))
```

`If` で囲うことで、**組織区分1 側が「不要」の種別（`―` 表示）はクリックしても何も起きない**。

### 未申請の変更を見せる

`colO2Edit` と `colOrg2All` を比べて、変わっているセルに枠線、行末に「● 未申請」を出す。
申請ボタンには件数を出し、0 件のときはグレーにする。

### 申請時（`btnO2Submit.OnSelect`）

1. 変更行を `colO2Chg` に抽出（変更前 / 変更後の両方を持たせる）
2. 0 件なら警告して終了
3. `PRM_Requests` にヘッダ（`ReqType = ORG2`）
4. `PRM_RequestItems` に明細（`ForAll(Sequence(...))` で連番を振る）
5. **`PRM_Org2` を実際に更新**
6. ヘッダを `APPLIED` に
7. `colOrg2All` を取り直し、`colO2Edit` を作り直す

> 権限変更の申請（`Submit.Grant.txt`）は申請の記録だけで `PRM_Grants` を更新しないが、
> **こちらは 5 でマスタを実際に更新する。** 承認フローが入るまでの暫定。

### 整合性チェック（仕様 §7）を申請前に出す

**要 → 不要 にすると、その組織区分2 を個別指定していた既存権限が条件を満たさなくなる。**
仕様どおり**自動では書き換えず、申請前に影響を提示する**。

表の下の説明文が、影響があるときだけ警告に変わる。

```
⚠ この変更で 1 件の既存権限が対象外になります（佐藤 一郎（外部接続申請担当））。
   権限は自動では消されません。申請後に個別に見直してください。
```

申請ボタンの文言も「影響を承知して申請」に変わる。

#### 判定

「変更後に対象外」かつ「**変更前は有効だった**」ものだけを数える。
前者だけだと、もともと条件を満たしていない権限（過去の不整合）まで並んで警告が読めなくなる。

```
対象 = ScopeType = "PICK" かつ Org2Codes にそのコードを含む権限
Bad  = 変更前に有効(colOrg1 + colOrg2All) かつ 変更後に無効(colO1Edit + colO2Edit)
```

判定に使う種別は権限で変わる（仕様 §5.4）。
`EXTCONN`/`WLAN`/`CLOUD` は対応する 1 種別、
`SECMGR`/`CONFORM`/`INFOSEC` は **3 種別のいずれか 1 つでも有効なら有効**。

> 実機で確認: `A0102` を個別指定している権限は 5 件あるが、外部接続だけを不要にしたとき
> 警告に出るのは外部接続申請担当の 1 件だけ。無線LAN 担当・クラウド担当・
> 適合化担当・情報セキュリティ担当は他の種別が「要」のまま有効なので出ない。

### 組織区分1 の要否も同じ形で変更できる

`colO1Edit` を編集用に持ち、`ReqType = ORG1` として申請する。

**組織区分2 側のガードは `colO1Edit`（編集中）を見る。**
組織区分1 を「不要」にした瞬間、組織区分2 の該当列が全行 `―` に変わり、
**連鎖する影響がその場で見える**。保存済みの `colOrg1` を見ると、
申請するまで影響が分からない。

`PRM_Org1` を更新したあとは `gblP1` も取り直す（マトリックスの判定に使っているため）。

## 12. 権限をマトリックスから変更する（実装済み）

組織マスタの要否編集（§11）と同じ「編集用コレクション + まとめて申請」の形。

### コレクションと名前付き数式

| コレクション | 中身 | 使う場所 |
|---|---|---|
| `colGrantsAll` | `PRM_Grants` の現在値（レコードそのまま） | 変更の有無の比較元 |
| `colGEdit` | `{Gid, O1, Role, Scope, Codes, CR}` に畳んだ編集中の値 | マトリックスの表示・クリック |

マトリックスが参照する式は**すべて `App.Formulas`（名前付き数式）に括り出してある**。
セルに直接書くと 1 セルにつき 20 回ほどコレクションを走査することになり、操作できないほど重くなる。

| 名前付き数式 | 中身 |
|---|---|
| `fMem` / `fPage` | 選択中の組織区分1 のメンバー / そのうち現在ページの 8 人 |
| `fG1`〜`fG8` | 各列のグローバルID（人数が足りない列は `""`） |
| `fP1` | 選択中の組織区分1 のレコード（多段階設定要否の判定に使う） |
| `fOrg2` | 選択中の組織区分1 の組織区分2（表示順） |
| `fChg` | `colGEdit` と `colGrantsAll` の差分（未申請の変更） |


`colGEdit` は `PRM_Grants` を**平らな文字列だけのレコード**に畳んである。
選択肢列（`RoleCode` / `ScopeType` / `CompanyRole`）は `.Value` を取り出して入れる。
ギャラリーの子から選択肢列をたどると解決しないことがあるため。

### 「全体」と組織区分2 の連動

クリックのたびに新しい `Codes` を作り、**対象の組織区分2 を何個含むかで `Scope` を決め直す**。

```
n = 対象の組織区分2 のうち Codes に入っている数
n = 0            → Scope = "NONE"（Codes は空にする）
n = 対象すべて   → Scope = "ALL" （Codes は空にする）
それ以外         → Scope = "PICK"
```

`ALL` と `NONE` のときに `Codes` を空にするのが要。残しておくと、
あとから対象の組織区分2 が増えたときに「全体のはずが一部だけ」になる。

### 申請の書き込み

`btnGrantSubmit` が `colGEdit` と `colGrantsAll` を突き合わせて `colGChg`（差分）を作り、

1. `PRM_Requests` に 1 件（`ReqType = GRANT`）
2. `PRM_RequestItems` に差分の数だけ（`ADD` / `UPDATE` / `DELETE`）
3. `PRM_Grants` を upsert（`Scope = NONE` は `IsActive = false` の論理削除）

の順で書き、最後に `colGrantsAll` / `colGEdit` を取り直す。

`Operation` は変更前後の `Scope` で決める（`NONE → 何か` = `ADD`、
`何か → NONE` = `DELETE`、それ以外 = `UPDATE`）。

> 実機で確認: 権限なし→全体 が `ADD` / `{"ScopeType":"ALL"}`、
> 個別（東北支店）→個別（北海道支店、東北支店） が `UPDATE` /
> `{"ScopeType":"PICK","Org2Codes":";A0102;A0101;"}` として記録され、
> `PRM_Grants` の `CompanyRole` は保持された。
